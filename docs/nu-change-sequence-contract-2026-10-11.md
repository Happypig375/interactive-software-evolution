# Nu change sequences: inherited state, obligations and recovery

**Decision, 2026-10-11:** R09 now has a proposed sequence and accounting contract supporting R02/R05. Its question is whether a useful representation/workflow difference survives later changes and recovery work. It is not a new long-horizon benchmark claim, a memory-policy experiment or an authorization to construct/run tasks. [PLAN](../PLAN.md) retains zero allocation and all execution holds.

## Main inheritance and information policy

For this proposed R09 extension, each independently assigned **sequence** starts from its arm's eligible baseline. Successive stages inherit that sequence's own submitted workspace. This deliberately differs from the study packet's independently initialized single-change tasks. The primary observational unit is the assigned sequence, with stages and obligations nested within it.

| State or information | Proposed main policy | What must be recorded |
| --- | --- | --- |
| Source and allowed project files | Preserve the actual submitted tree, including permitted untracked files, candidate-written tests, dependency declarations and durable project notes. Never replace it silently with a reference repair. | Predecessor/submission identities and hashes; allowed-file manifest; source/dependency changes and missing artifacts. A Git commit alone may omit relevant untracked files. |
| Environment and installed dependencies | Recreate the declared environment and restore the submitted project files at each stage. Reinstall permitted dependencies from the submitted declarations under the fixed policy. | Toolchain/package identities, reinstall/setup work, caches and failures. Workspace inheritance does not imply a persistent container; ad hoc shell/package state is not silently carried. Actual supported execution remains unverified. |
| Agent conversation | Start a fresh conversation with the same fixed policy and the active public requirement prefix. | Prompt identity and all supplied prior information. Durable repository notes/tests still carry agent-authored information; fresh conversation is not memory-free execution. |
| Development feedback | Permit the same declared source navigation, builds, public tests and ordinary tools in both arms. Preserve allowed prior tests but version any supplied test whose requirement has explicitly changed. | Actual feedback and cost, including build failures exposed by the inherited source. Candidate tests may be revised, removed or replaced safely; their presence is not final evidence of correctness. |
| Final evaluation | Evaluate a frozen submission in a separate evaluator copy, with no scoring result or hidden artifact fed into the next candidate stage. | Source/requirement/oracle versions, observable outcomes, coverage and missingness. Evaluation must not mutate the inherited candidate workspace. |

Freeze per-stage resource rules and any sequence-wide stop condition before assignment; give both arms the same rule. This document chooses no model, allowance, stage count for sampling or extra worker. Retain the existing backend, transport and security decisions. Count setup, reading retained notes, self-repair and validation; unused allowances do not authorize further work. A change to retained conversation, environment persistence or tool access would be another policy comparison, not a free implementation detail.

Ordinary continuation begins from the prior submission whether it passed, failed or was not fully observed. A build failure can be diagnosed and repaired during the next stage using permitted development feedback and that stage's allowance. Preserve both the failed original and the later recovery. If the candidate changes organization or abandons its original style, retain the attempt and count the work; style conformity is not an outcome filter.

Safety, resource and infrastructure stops still apply. Record whether later slots were assigned, actually attempted, unattempted because the sequence stopped, or unevaluable. Do not manufacture successors, silently grant rescue time or call every unobserved slot a semantic failure. A final-test failure alone must not trigger extra candidate work or determine whether it receives the next scheduled requirement.

## Reference and rescue policies answer different questions

The main contrast follows **actual inherited histories**. Two optional diagnostics would require separate preparation and allocation:

- A **clean reference predecessor** satisfies the already public requirement prefix before the next task. It asks about the next change from a controlled state. It does not measure the cumulative cost of producing that state, estimate actual-history success or authorize reference-solution exposure in the main arm. Reference construction/validation and any visible prior tests must be documented; no future requirement may select the reference or an accepted agent predecessor.
- A **repaired predecessor** starts from an actual failed submission plus a declared rescue procedure. It asks about assisted recovery. Record who repaired what, the information used and all time/model/tool work; keep the original outcome and branch identity. A maintainer's repair or human-authored code is not autonomous agent success or evidence for R21 steering effectiveness.

These are different policies, not three mandatory equally funded arms. One reference/inherited discordance does not prove earlier code caused the later failure: task difficulty, unequal information, stochastic execution and other state differences remain alternatives. A future direct context-policy intervention would instead need cloned predecessor/source/requirement conditions; it cannot infer a pure memory effect from independently diverging histories.

## Outcomes, regression and cost

Keep a matrix of obligations by **submitted stage**, evaluated against the versions active at that stage. A retained obligation requires a comparable exercise/observation before and after the change to classify its transition:

| Earlier observation | Later observation | Permitted interpretation |
| --- | --- | --- |
| Pass | Pass | Retained observed behavior at the declared coverage. |
| Pass | Fail | Newly observed regression under comparable conditions; this alone does not identify the causal edit/mechanism. |
| Fail | Pass | Recovery of an inherited failure. Preserve the original failure and charge the recovery work. |
| Fail | Fail | Persistent observed failure, rather than a newly introduced regression merely because it is seen again. |
| Unknown in either position | Any | Incomplete transition evidence; preserve the known observation without inventing the missing one. |
| Rule retired or materially revised | Different active rule | Score against the new rule and retain the historical result separately; do not compare incompatible predicates as the same obligation. |

Report distinct endpoints:

1. **Per-stage verified delivery:** all active obligations established within that stage's allowance. Use every assigned stage in the disposition/accounting table; nonverified outcomes receive no delivery credit, with demonstrated failure, missing observation and nonexecution kept separate.
2. **Delivery across the sequence:** whether every required intermediate submission met its then-active contract. A known failure prevents an all-stage success; incomplete observations remain explicitly unresolved. Later repair does not rewrite earlier delivery.
3. **Final cumulative behavior:** whether the final submission meets the final active requirement set. A sequence may recover to a valid final product after earlier failed delivery; report that useful outcome without hiding the failures or recovery cost.
4. **Total work and resources:** cumulative implementation, failed attempts, setup, reading/reconstruction, repair and verification across the assigned sequence. Keep runtime performance, model traffic/priced expenditure, elapsed time and human assistance separate. Missing cost data is not zero, and success-only average effort is not the total policy effect.

Preserve separate counts for attempted submissions, available artifacts, evaluated obligations and assigned sequences. Stages, frames, obligations and cosmetic variants do not create independent applications or participants. Paired comparisons must use actual common assigned sequence identities and disclose attrition; neither complete-case filtering nor repeated-success selection can define the primary result after outcomes.

Task scope, source size, requirement revisions and inherited failures can explain a cost curve. Patch spread, helper count, source compactness and diagnostic exposure are intermediate observations, not maintainability outcomes or grounds for post-treatment adjustment to claim a pure mechanism. Preserve the existing E/H adverse compactness findings. No human-steered productivity, universal language ranking or broad population prevalence follows from this candidate.

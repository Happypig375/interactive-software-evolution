# Nu's 2D platform route and a common behavior contract

**Decision, 2026-10-11:** C-platform is now a source-grounded R01 package candidate with a concrete behavior boundary. Begin the proposed Nu route with an ordinary dynamic capsule rider and kinematic platform; retain the dedicated character solver as a separately configured alternative, not an assumed stronger default. This is a design selection for review, not a constructed scene, proven capability or allocation. R02's existing Blaze Vector pair still needs its own eligibility and alignment decision. All holds in [PLAN](../PLAN.md) remain.

The [task-diversity audit](nu-task-diversity-and-common-requirements-2026-10-11.md) supplies the public #1020/#1109 requests, Blaze Vector mismatch register and ordinary Godot platform facilities. This continuation resolves the Nu source dependency and applies [R05/R06's observation and cost rules](nu-research-study-designs-2026-10-08.md). Public requests, implementation reasoning and the authored requirements below are distinct evidence.

## Pinned implementation and package boundary

Nu source remains `064f7ae92a8506689cd91aff5e6804a375d6ef3d`. The default [NuPlugin.MakePhysicsEngine2d](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/World/WorldTypes.fs#L2302) constructs Box2dNetPhysicsEngine. This binds a source route, not the engine actually loaded in a running process.

[Nu.fsproj](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/Nu.fsproj#L186) declares Box2D.NET **3.1.1.557** alongside other physics dependencies. Its [NuGet manifest](https://api.nuget.org/v3-flatcontainer/box2d.net/3.1.1.557/box2d.net.nuspec) identifies repository commit `d72ce440f6d409c3e15720a66b060051e7fdb87d`. The [pinned README](https://github.com/ikpil/Box2D.NET/blob/d72ce440f6d409c3e15720a66b060051e7fdb87d/README.md) describes a **pure C# port**, not a native Box2D wrapper. The [package page](https://www.nuget.org/packages/Box2D.NET/3.1.1.557) and complete manifest were inspected; no package was installed, binary/build correspondence established or resolved assembly observed. Selected body and collision-plane definitions at the recorded commit were also read. The solver's separate upstream-example link names another revision and remains unread; it is not silently substituted for the package edition.

Thirteen Nu files, the manifest and four dependency source files were acquired with byte counts and SHA-256 hashes. Except for the complete ToyCharacter/plugin and dependency files, coverage is selected code ranges, not whole-engine reading. The [search ledger](literature/nu-background-searches-2026-09-30.md) records those ranges and decisions. No publication-reading credit or Zotero change follows.

It checks grounding unless air jumping is allowed, then adds velocity opposite that direction. Its body lookup is not restricted to KinematicCharacter, despite the narrower comments in [PhysicsEngine](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/Physics/PhysicsEngine.fs#L142) and [WorldPhysics](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/World/WorldPhysics.fs#L408). This comment/implementation/sample difference is an API-understanding cost, not an observed failure.

For dedicated characters, [solveCharacter 1595–1666](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/Physics/Box2dNetPhysicsEngine.fs#L1595) uses its own stored gravity scale/override, ground cast, pogo state and collision planes. The jump-direction lookup does not read those character fields. Their consistency under nondefault per-character gravity is unverified; the ordinary-body path does not prove it. The inspected solver/collision callback contains no explicit transfer of a support body's velocity or selectable departure policy. This is a bounded source observation, **not proof that moving bodies cannot carry riders**: contact solving and application code can contribute motion. Use fixed nonzero downward gravity for the first candidate; defer arbitrary/changing gravity and dedicated-character guarantees.

## Proposed common behavior

This prose contract adapts #1020; it is not a recovered issue specification or an executable task. R01 may use each package's ordinary idioms, including Godot's already credited CharacterBody2D/AnimatableBody2D facilities. Do not add a new experimental arm for every Nu body mode or make Godot imitate Nu. For R02, retain the original Blaze Vector implementations until a separate alignment rationale explains their existing GravityIgnore/custom movement and input differences; importing the sandbox avatar wholesale would change the package being studied.

| Obligation | Selected semantics for review | Observation and boundary |
| --- | --- | --- |
| Small common scene | One upright capsule rider and one flat, horizontally translating platform under constant downward gravity. No enemies, projectiles, random section choice, slopes, stairs or rotating supports in this case. A stationary-platform predecessor and a moving-platform successor retain the same rider/input contract. | Declare matching geometry and units; record the initial settling phase and any failure. This family does not stand in for the separately retained contact/score or history questions. |
| Movement and carrying | With no directional input, a supported rider follows platform translation within a prospectively chosen positional tolerance. Left/Right requests move relative to the support; opposing keys cancel. | Observe platform and rider position/velocity, support relation and elapsed logical time. A collider touching the rider or a true grounded flag alone does not establish carrying. |
| Jump and departure | One nonrepeated Space press while supported requests one jump opposite gravity. No air jump or grace period in this first case. On departure, preserve the support's horizontal velocity **once** in world space, with no double addition to an already carried rider. | Continued key holding must not produce another jump. Freeze the launch-speed and permitted numerical error before assignment. Different correct physical/control implementations remain valid. |
| Pause and resume | Pause stops logical movement and jump acceptance while leaving the host/editor responsive. Resume preserves the existing supported state; input pressed only during pause does not become a queued jump. | Compare declared logical boundaries, not wall time or an assumption that every host callback stops. Require a fresh press after resume; record missing phase/input access as inconclusive. |
| Removal and exit | Removing the platform clears eligibility to jump from it and ends carrying by the next declared completed logical update. Exiting the scene prevents its later movement/jump cues from affecting the successor scene. | Track entity lifetime as well as address. Do not require a removal-generated separation callback unless that is the chosen public contract; absence of stale influence is the behavioral requirement. Same-address recreation is a separate stress extension, not silently certified. |
| Effects | One jump cue per accepted jump; none for rejected/paused presses, mere resume, support removal or an old scene's queued work. No scoring mechanic is included. | Count actual requested/delivered effects at a declared boundary. Already emitted sound is not rolled back. The observation method must not implement the missing gameplay logic. |

For a concrete review scale, use rider height **H = 1**, capsule width **0.5H**, platform width **4H**, horizontal platform speed **H/s**, requested walking speed **2H/s**, jump-speed increment **4H/s** and gravity magnitude **9.80665H/s²**. Propose **60 logical updates/s**, a **0.25 s** initial settling allowance and a **2 s** no-input carry interval with no more than **0.05H** relative horizontal drift. These are authored candidate parameters, not measured feasibility or a calibrated final oracle. Before any assigned attempt, later authorized preparation must justify/freeze geometry, phase, tolerances, event ordering and eligible initial state together. Preserve unsuccessful preparation and any prospectively revised contract; do not widen tolerances after seeing treatment outcomes.

The current Nu defaults include [Meter2d = 32](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/Core/Constants.fs#L64), four 2D substeps and a 45-degree ground-angle threshold. They are configurable, not observed effective settings. Nu [converts body velocities](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/Physics/Box2dNetPhysicsEngine.fs#L1285) to the dependency's physics units; the pinned [B2BodyDef](https://github.com/ikpil/Box2D.NET/blob/d72ce440f6d409c3e15720a66b060051e7fdb87d/src/Box2D.NET/B2BodyDef.cs) describes metres/second. Map H, coordinate direction and time explicitly in both packages. Equal pixel values or identical solver settings are not required; equivalent intended behavior at the declared tolerance is. The backend [clamps positive integration deltas](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/Physics/Box2dNetPhysicsEngine.fs#L1882) to 0.001–0.1 seconds and skips zero-time integration. That policy belongs in the timing record.

## Observation, identity and cost limits

Public [grounding APIs](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/World/WorldPhysics.fs#L133) expose normals/tangents/grounded state. They do not expose the dedicated solver's private OnGround shape as a public support-identity getter. [Physics messages](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/Physics/PhysicsEngine.fs#L148) carry source/target body-shape identities and directional penetration normals. Dedicated-character support changes [emit separation/penetration messages in both directions](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/Physics/Box2dNetPhysicsEngine.fs#L1996). Those events can inform a future observer, but generic contacts are not automatically support, and duplicate directions are not two independent interactions.

Phase matters. [World.processPhysics2d](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/World/WorldModule2.fs#L1936) publishes the integration batch **before** applying each message to the world. Entity messages are subsequently published only for existing, selected entities. The [main loop](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/World/WorldModule2.fs#L1986) processes input, physics, pre-update, update and post-update in that order. An integration-event callback reading entity transforms can therefore be at a different boundary from the batch it receives. Later observation must distinguish raw physics results, applied transforms and completed gameplay obligations; no agent-access route or correctly placed monitor is verified here.

[BodyId equality](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/Physics/PhysicsPrelude.fs#L12) uses simulant address and body index; the source calls it ephemeral and not intended for persistence. Equal addresses are insufficient to certify one uninterrupted lifetime after removal/recreation. [Body destruction](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/Physics/Box2dNetPhysicsEngine.fs#L1156) removes that body's dictionaries and underlying body; the inspected method does not explicitly clear other characters' OnGround references. The later support-change path reads old-ground user data. This makes removal a consequential observation case; it is not a demonstrated stale-handle crash or proof that all intervening cleanup is absent.

For R06, distinguish **managed Box2D.NET physics reconstruction** from the [separate native Jolt route](nu-jolt-dependency-audit-2026-10-11.md). Box2dNetPhysicsEngine [ClearInternal](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/Physics/Box2dNetPhysicsEngine.fs#L2083) clears bodies/character state and creates a new physics world before destroying the old one; it passes the existing contact tracker to the new context. This does not establish complete tracker reset, body-state serialization or rewind of contact/solver history. Count setup, source/documentation discovery, alignment, application carrying logic, observation, physics rebuilding and resumed behavior. Neither the port's implementation language nor a cheap retained world root establishes low total cost.

## Disposition and remaining decision

The API-name and old-issue ambiguity is resolved sufficiently to prepare the bounded R01 candidate. The ordinary dynamic/kinematic route is a credible starting hypothesis, not certified carrying behavior. Dedicated pogo characters remain an alternative with explicit configuration and gravity/support limits. C-gravity becomes an existing-capability/adaptation check if later promoted, not an assumed missing Nu innovation.

The next consequential action for this case is a **separate feasibility/construction decision** on the common scene, phase-correct observations, actual package/tool access and a practical work boundary. Do not infer permission from this contract. R02 retains its mismatch/alignment gate; R03 retains the selected Breakout B0/B1 gate; R04 retains source-equivalence/diagnostic/oracle gates. A failed carry/removal case or cheaper ordinary Godot integration is legitimate adverse evidence. Source inspection cannot establish that result, human adoption value or steering effectiveness. Continue another direction's accessible consequential dependency while these execution decisions remain held.

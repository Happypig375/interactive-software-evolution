# Task diversity and common requirements beyond Breakout

**Decision, 2026-10-11:** retain Blaze Vector as a second application candidate for R02 and a source for an additional R04 convention site. Its existing MMCC/ImSim pair is **not yet an equivalent baseline pair**. Public requests give moving-platform and gravity-relative movement requirements useful provenance for R01/R02, but their implementation and evaluation remain conditional. This audit prepares comparisons; it changes no hold or allocation in [PLAN](../PLAN.md).

The [study designs](nu-research-study-designs-2026-10-08.md) remain authoritative for outcomes and accounting. The [Breakout history contract](nu-history-application-contract-2026-10-11.md) remains the first R03 technical case; the native character/control state here is not silently added to that recovery promise.

## Scope and provenance

At Nu `064f7ae92a8506689cd91aff5e6804a375d6ef3d`, the complete tracked `Projects` path inventory contains 1,907 paths across eleven immediate project directories. Two named pairs are Breakout and Blaze Vector. A filename inventory establishes available examples, not the completeness, functionality or independence of those applications. Twenty-two selected Blaze Vector F#/project files and four configuration/overlay files were acquired and read completely. Plugins and most asset bodies were not read. A Git object comparison found 171 common asset paths, 170 identical blobs and only `Gui/Title.nugroup` different; there are no asset paths exclusive to either pair member. Shared assets do not establish identical execution or random level selection.

Three native GitHub issue queries requested 100 results on page 1: exact “Blaze Vector” returned 6/6, “jump” 5/5 and “collision” 7/7, all with `incomplete_results=false`. Their 18 positions contain 17 distinct issues. Titles were screened; seven complete issue bodies and all twelve returned comments were read. These narrow query ranges are exhausted, not the repository or the field. Exact queries, identities, dispositions and source hashes are in the [search ledger](literature/nu-background-searches-2026-09-30.md).

No new paper, PDF reading credit, Zotero record, experiment, human participant or independent review follows. Public requests, historical implementation accounts, source reasoning and authored research requirements retain separate provenance.

Cosmetic variants of these requirements do not add independent families. A local lifetime change and a coordinated platform/grounding change address different work, but their feasibility costs and uncertain value are not made equal by assigning equal task counts. Keep low-cost adverse cases and legitimate default behavior when they test the proposed explanation.

## R04: an additional authentic convention site

The existing MMCC [BulletCommand](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Projects/Blaze%20Vector%20Mmcc/Bullet.fs#L8) has Update and Penetration. Its final Penetration arm calls `World.destroyEntity entity world`. Replacing only that last pattern with a catch-all has a source argument for the same current ordinary two-case behavior; no source variant was built and invalid/null representations are not certified. This is the same D1 convention contrast as [the Breakout site](nu-comparator-and-convention-audit-2026-10-11.md#r04-an-authentic-existing-source-site), within one implementation—not an MMCC-versus-ImSim experiment.

A future lifetime-renewal command would need to preserve the projectile and change its expiry basis; a cancellation command could legitimately share the existing destruction default. Changing the lifetime value without adding a command case supplies a no-case-extension contrast. These are related authored sketches, not three independent task families. Their trigger design and the accessibility of required model updates remain later feasibility work. Compile diagnostics, actual retained behavior and deadline/identity obligations must remain separately recorded. A correct catch-all, different safe organization or explicit handling of cancellation remains valid.

## R01: common package requirements and an ordinary alternative

A bounded 2D platform interaction is a plausible common application requirement, with #1020 as motivation. Use one declared Nu workflow and the provisional ordinary Godot 4.7.2/GDScript package from the [comparator audit](nu-comparator-and-convention-audit-2026-10-11.md). Do not force Godot to copy Nu's architecture or automatically add both Nu styles as new R01 arms. R02 owns that separate comparison.

At Godot engine pin `ed1daf0bf001b61586d9930840f2f1394092c079`, the [CharacterBody2D contract](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/CharacterBody2D.xml#L140) describes moving-platform velocity propagation during movement, configurable floor/wall layers and three departure-velocity policies. Its `up_direction` defines floor/wall/ceiling classification; it does not supply the application's whole gravity policy. [AnimatableBody2D](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/AnimatableBody2D.xml#L6) supplies ordinary scripted/animated moving-body support with physics synchronization. These shipped facilities belong in the credible alternative. Selected documentation was read, not implementation internals or runtime behavior.

The common contract must fix a level/obstacle/platform geometry, coordinate/unit mapping, logical timing, player input/grace/cooldown policy, support/carry/detachment conditions, interaction/score rules, pause/exit behavior and included effect multiplicity. Match the realized level sequence rather than assuming shared random calls. Require equivalent intended behavior at declared tolerances and event boundaries; exact native handles or identical cross-engine solver trajectories are not adoption outcomes. Count scene/asset setup, documentation/navigation, application code, debugging, preservation work and runtime costs. Useful nulls include Godot's ordinary platform support dominating integration effort, or neither workflow producing reliable continuation within the proposed scope.

## Disposition and next work

R02 has a second source-grounded application candidate with an explicit mismatch register; R04 has a second existing convention site; R01 has practice-motivated common requirements and a stronger ordinary comparator. This advances diversity preparation without claiming representative sampling, clean baseline equivalence, measured benefit or whole-field completion.

The remaining decisions are concrete: which existing behavior defines the common contract, whether the selected Nu platform/character route can support it without an unapproved adapter, and whether a small D1 lifetime case has enough decision value to justify feasibility. Resolve a selected source dependency when it can change that choice; inspect broader history or literature when a stronger scope/novelty claim requires it. Launch, baseline alignment, temporal/oracle exercise, agent access and resource allocation remain separate, held work. Preserve all attempts and the historical E/H counterevidence.

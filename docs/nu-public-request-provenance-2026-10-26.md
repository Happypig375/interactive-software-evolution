## A real request does not specify the research treatment

[#1366](https://github.com/bryanedds/Nu/issues/1366), opened 13 May 2026,
requests four customizable directions: left-to-right, right-to-left,
top-to-bottom and bottom-to-top. The current thread has no comments. Its
enhancement/ease labels do not establish implementation, development effort,
customer priority or observed success. No particular game or maintainer's
willingness to pay is stated.

The source check reads `FillBarFacetExtensions` and `FillBarFacet`, lines 842-904,
at both the [research pin](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/World/WorldFacets.fs#L842)
and the [revision returned by the current code search](https://github.com/bryanedds/Nu/blob/caa06b027fd412deeadc3f85ca419005b369a1af/Nu/Nu/World/WorldFacets.fs#L842).
Those selected spans are identical; the complete files differ. The facet
defines fill amount, inset, color/image and border properties. Its render path
clamps the amount to [0,1], scales the fill width and anchors its position at the
left edge plus the inset. It does not select among directional cases or read a
direction property. This describes that built-in path, not the absence of all
possible application helpers, custom facets or alternate renderers. No rendered
output or runtime behavior was observed here.

The [pinned Godot ProgressBar class reference](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/ProgressBar.xml)
already exposes four fill modes. Its
[drawing and property-binding source](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/scene/gui/progress_bar.cpp#L115)
implements that selection. Horizontal modes are relative to text-layout
direction, so a physical left/right requirement must bind the layout setting;
top/bottom modes are explicit. The [4.7 manual](https://docs.godotengine.org/en/4.7/classes/class_progressbar.html)
agrees. This extends the existing [ordinary-comparator inventory](nu-comparator-and-convention-audit-2026-10-11.md)
at its already selected engine commit, not an unpinned latest-release substitute.

These facilities are not visually equivalent just because both accept a
fraction or direction. Theme minimum sizes, rounding, borders, inset semantics,
layout and range/value conventions still require a common output contract.
Allow ordinary shipped configuration and valid application-level alternatives;
do not require an engine modification when one is unnecessary. Count whatever
setup, extension, asset work and verification the actual solution needs.

This request also **does not supply a mined D1 case-extension task**. The
inspected render path has no existing direction union or match to extend.
The issue's four names do not by themselves require a particular public F# ABI.
Introducing an initial direction representation, or inventing a later fifth
case, is different from observing a real request to extend an existing domain.
Any such follow-on must retain its authored status. Keep D1's current initial-
convention comparison and valid-alternative rule unchanged.

### History and language boundaries that affect the design

The selected [UndoRedo implementation](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/core/object/undo_redo.cpp#L204) records object IDs, references where applicable and supplied property values. Its [commit path](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/core/object/undo_redo.cpp#L315) applies operations and evicts old actions when `max_steps` is positive. The operation loop skips a target that has already disappeared. This makes object lifetime, value/alias choice, explicit reference retention and action ordering part of application correctness, even when the API call succeeds. It is source reasoning, not a reproduced defect or measured cost.

Nu's retained world roots and service reconstruction and Godot's registered actions/copies are different supported starting points. A later history comparison must first select the same promised outcome: inspect a fault, restore declared gameplay values, or resume with outstanding obligations. Charge each package for the integration necessary to obtain that outcome, retaining a cheap ordinary debugging solution as valid. A within-Nu retention ablation remains R03/R06; it should not be replaced by this cross-engine package contrast.

The [C# documentation](https://github.com/godotengine/godot-docs/blob/9adca4c1c72917bfe1b7be3108abed5ce26696a6/tutorials/scripting/c_sharp/c_sharp_basics.rst#L31) requires a .NET-enabled editor and separate SDK, recommends external editing/debugging, and requires assembly rebuilds for changed exported members/tool scripts. Its [hot-reload caveat](https://github.com/godotengine/godot-docs/blob/9adca4c1c72917bfe1b7be3108abed5ce26696a6/tutorials/scripting/c_sharp/c_sharp_basics.rst#L286) lists exported variables as an exception to state not being saved/restored. The selected prose does not settle editor versus running-game coverage for every C# reload operation; no C# workflow or hot-reload implementation is validated here. Its SDK paragraph still names Godot 4.5, so it is not an exact 4.7.2 SDK pin. These are explicit follow-ups if C# is selected, not grounds to weaken the GDScript comparator.

[S296 State Explorer](literature/full-reading/S296-S297-state-exploration-and-live-replay.md) remains a separate research-plugin alternative with documented state/action isolation work. Neither that reading nor this inventory verifies a current 4.7.2-compatible release. A research extension, ordinary programmable undo and the shipped editor workflow are distinct packages, not interchangeable labels for the control condition.

**Decision:** retain ordinary Godot/GDScript as a credible R01 candidate. F-local and F-lifecycle have documented native facilities; eligibility still requires an authentic application and common initial/required behavior. F-history is conditional on a selected promised boundary and honest integration accounting. No adoption-value estimate, general absence claim, binary compatibility or agent-tool accessibility follows from this inventory.

### Checked-in compiler policy is not a frozen toolchain

The [Breakout project](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Projects/Breakout%20Mmcc/Breakout%20Mmcc.fsproj#L15) sets warning level 5 in its Debug/Release AnyCpu groups. It enables FS1182 and suppresses six named warnings; FS0025 is not among them. Its explicit error list is FS0026, FS0049 and FS3239 **plus inherited `WarningsAsErrors`**. It does not itself promote FS0025. The [engine project](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/Nu.fsproj#L13) has the same explicit error list and no FS0025 suppression.

The application targets `net10.0`; pinned [CI](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/.github/workflows/CI.yml#L13) requests floating `10.x` and invokes ordinary build/test commands. The tracked-tree scan finds no `global.json` or `Directory.Build.props/targets` at this revision. The engine's [FSharp.Core package entry](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/Nu.fsproj#L210) names 10.1.300; this is not an exact compiler identity. External parent imports, invocation properties, SDK resolution and effective conditional properties were not evaluated.

**Preparation decision:** carry the existing warning-only expectation forward provisionally, with the same policy in both arms. Before execution, freeze an exact SDK/compiler, resolved properties and ordinary output-delivery policy, and observe the site's actual diagnostic. If the final protocol deliberately promotes FS0025 to an error, declare that departure in advance for both arms; it changes the ecology under study. Do not infer enforcement from the coding standard's preference for exhaustiveness.

The serving and pause requirements deliberately point in different directions for the same current fallback. They still share one application and substantial lifecycle/content logic, so they cannot establish broad independent coverage. The no-extension control illustrates a distinct editing demand; it is not automatically exchangeable in effort with either extension. Partition development examples and evaluation tasks before any model observation, and obtain broader source/practice provenance before claiming a representative task portfolio.

The diagnostic sheet concerns source assignment and potential tool output. The behavior sheet concerns requirements, permitted alternatives, actual triggers, old/new observations and missingness. A returned warning is not evidence of agent attention; a cleared warning is not a pass. A correct catch-all remains a valid result, and a source transformation that changes initial behavior makes the proposed contrast ineligible until corrected under separate authorization.

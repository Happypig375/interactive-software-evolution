# Nu interaction replacement: the behavior that must survive

**Decision, 2026-10-11:** prepare R13 as a bounded contract supporting R02/R05, conditional on a useful preservation or verification-effort question. Start with replacing or extending Breakout's existing paddle controls. This supplies a concrete boundary for comparing data compatibility with behavioral preservation; it does not establish a new theorem, a Nu-specific advantage or an executable verifier. All construction and experimental holds in [PLAN](../PLAN.md) remain.

## Actual source boundary

All source uses Nu **`064f7ae92a8506689cd91aff5e6804a375d6ef3d`**. [MMCC Gameplay.update](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Projects/Breakout%20Mmcc/Gameplay.fs#L85) contains a paddle-control block before ball movement and collisions. When Playing with positive lives and remaining bricks, Left moves X down by four, with a lower bound of -128; otherwise Right moves X up by four, with an upper bound of 128. Left takes precedence when both are down. The other vector coordinates and paddle size are retained. With finite starting X in [-128, 128], this block preserves that bound. It is four units per eligible update, not a measured or time-normalized speed.

This is an existing **block inside a larger update**, not an inspected pluggable input-policy interface. Extracting a helper, adding an input snapshot or introducing a verifier would be new implementation work. The [ImSim control block](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Projects/Breakout%20ImSim/Gameplay.fs#L114) has the same local movement/priority rules but updates an entity and explicitly checks world advancement; its surrounding Process also checks selection. That local correspondence does not erase the two applications' different collision, state and lifecycle machinery. Keep the [R02 package attribution](nu-source-contracts-and-scenarios-2026-10-11.md) intact.

Three host boundaries matter before treating the update as a mathematical state transition:

- [World.isKeyboardKeyDown](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/World/WorldInput.fs#L113) ignores its world argument, reads ImGui's global keyboard-capture flag and then KeyboardState. Captured input returns false. The supplied world value is not a keyboard snapshot. The nearby isKeyboardKeyUp path does not apply that capture check, so replacing the down query with a negated up query does not preserve the inspected capture policy automatically.
- [Automatic screen scheduling](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/World/WorldModule2.fs#L1466) captures advancement and selection before game/screen processing. It conditionally calls [World.updateScreen](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/World/WorldScreen.fs#L142), which invokes the dispatcher and publishes UpdateEvent. Gameplay's [definition and message handler](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Projects/Breakout%20Mmcc/Gameplay.fs#L203) connect that event to Gameplay.update. Directly invoking Gameplay.update bypasses the scheduling gates. Changes after the scheduler captures its flags need an explicit interleaving policy; a global instantaneous-pause guarantee does not follow from this path.
- The [MMCC Message signature](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/World/WorldModule2.fs#L2923) receives World and returns signals plus a model. The actual Gameplay.update calls [World.playSound during collisions](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Projects/Breakout%20Mmcc/Gameplay.fs#L109), and ball reset can obtain a new random direction. Returning an immutable model through `just` does not make the complete handler pure or confine every effect to the Command method.

The useful positive capability is an explicit typed model/message/command organization and an inspectable local state update. Its host types express data shapes and callback compatibility; the inspected signatures contain no predicates for clamp bounds, key priority, effect counts or valid future play. This is a claim about these signatures and code, not proof that no additional Nu checking tool could exist.

## Proposed replacement and extension requirements

These are **authored adaptations of the existing L-control site**, not mined feature requests or independent task samples. Their practical importance remains to be established. Keep the model schema, gameplay rules, dispatcher and ordinary event route fixed for this preparation; live reload is R10's separate question.

For a replacement, use A/D in place of Left/Right. Compare corresponding input traces: old Left corresponds to new A and old Right to new D, with the same capture state and eligible updates. Preserve the old left-priority movement relation under that mapping. An unmapped raw-key trace is not necessarily behaviorally equivalent, because changing which physical keys control the game is the intended change.

For an extension, retain arrows and add A/D aliases. Specify the combined logical requests as Left-or-A and Right-or-D, **with left priority across all aliases**. If the new keys remain up, legacy input traces must retain the old behavior. With A and Right held together, the authored policy selects left. This priority is a requirement choice, not something guaranteed by giving both recognizers Boolean output types. Simultaneous same-direction aliases must not cause two movement steps during one invocation.

At the local block boundary, let L and R be the effective logical requests after the capture policy. With the eligible gameplay guard and finite X in range, require:

| Condition | Required X after one block invocation | Retained obligations |
| --- | --- | --- |
| L, whether or not R | max(-128, X - 4) | Preserve Y, Z and paddle size; one movement step. |
| Not L and R | min(128, X + 4) | Preserve Y, Z and paddle size; one movement step. |
| Neither request, including captured keyboard input | X | No movement introduced by control handling. |
| Gameplay guard false | X | The gameplay update's inactive branch retains the model; the control change must not bypass it. |

The local replacement must not directly change score, lives, bricks, ball state, time, subscriptions or external effects. This is a **boundary obligation**, not a demand that the entire following frame leave those values unchanged: ball movement, collision, sound and life handling legitimately run afterward. Observing only final-frame equality can hide a wrong intermediate control step or misattribute a legitimate downstream change.

Specify a coherent keyboard/capture sample during the invocation and no intervening selection/advancement change for the first bounded case. The present code performs separate host queries; it does not supply the proposed snapshot as a represented value. A future change in polling phase, deferred delivery, gestures, held-versus-pressed interpretation, duplicate handlers or callback reentrancy changes this contract and needs its own treatment. No new input recorder, recognizer, observer or seam is built here.

## What a local preservation claim can and cannot establish

For equal admissible entry states and corresponding effective inputs, equality of the paddle block's output plus its requirements for preserved state and effects is a useful **local proof obligation**. It could justify keeping the following code unchanged under stated host assumptions. It is not yet a proof that the complete programs have equivalent traces: the downstream program includes collisions, randomness, mutable host input, lifecycle changes and effects. An extension intentionally changes some raw-input traces. Its preservation claim must name the legacy subset and the new obligations separately.

[S298's completed interaction-typing reconstruction](literature/full-reading/S298-interaction-typing.md) supplies the close distinction: equal exposed data can let clients be reused, while recognizer behavior, device-specific predicates and configured conflict checks impose additional obligations. Nu's proposed key mapping is not an implementation of Interacto's interaction algebra. Its actual checks cannot be credited to Nu, and a lack of diagnostics does not validate the alias-priority rule.

[S299's completed modular-verification reconstruction](literature/full-reading/S299-modular-reactive-verification.md) supplies behavioral implication and relevant exit-condition obligations under explicit world models. Its theorem concerns memoryless action selection over decision structures, with world-state and model assumptions. A stateful Nu frame loop is not automatically one of those structures. The paddle block has ordinary control-flow continuation, not an established S299 module/return-label mapping. No theorem transfer is asserted; constructing and validating such a model would require separate authority. A sufficient local condition failing also need not mean every permitted implementation is incorrect.

## Comparison, observations and promotion

The first useful comparison would hold the application and requested behavior fixed and compare ordinary typed development/review with development supported by an explicit boundary contract and its justified checks. This is a workflow-information comparison unless a specific implemented mechanism can be isolated. Both workflows receive the same behavioral requirement and ordinary allowed tools; a contract/checker must not hide successor implementation code or final scoring feedback. Charge contract/model creation, input/phase access, checking, false alarms, repair and maintenance. Preserve valid reorganizations and every assigned attempt.

Use [R05's observation rules](nu-research-study-designs-2026-10-08.md#r05--correctness-of-interactive-change) for later cases: distinguish compiler acceptance, contract-check coverage, local state/meaning, effects and completed behavior. Prose challenges include both-direction priority, duplicate aliases, clamping at each edge, captured input, inactive gameplay, held-versus-edge-triggered motion, a wrong coordinate/size update and duplicated effects. Correct alternatives remain admissible; these examples are not executed tests, mutants or independent fault samples. Missing input/phase evidence makes the relevant result inconclusive.

R13 now has a source-supported contract to review. **Keep it conditional as a standalone study.** A useful next decision is whether preserving a consequential obligation or reducing total verification work justifies preparing a richer boundary. Simple key remapping alone may offer little new research value beyond an R02 task and R05 validation case. Promote only when the guarantee or effort question exceeds restating known typing/modular-verification principles, and the benefit is large enough to matter to an intended workflow. This audit changes no allocation, source implementation, runtime result, human-study authority or historical E/H evidence.

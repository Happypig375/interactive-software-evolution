## Mechanism and integration obligations

Pages 1–6 motivate a broad economy subsystem: resources include objects, health, mana, troops and information, not only currency. The difficult cases combine changing specifications, unanticipated entity types/access patterns and mechanics that modify other mechanics. The authors use the iterative ProSA-RA process, drawing on literature, public code and USPGameDev experience to derive requirements, design and evaluate successive architectures. Predicate dispatch, property-centric ECS and Adaptive Object-Models are explicit foundations.

The architecture has three concerns: integration with other subsystems, the mechanics model, and iterative development. A **Record** holds economy state as entities and properties. A **Rule** has a keyword, applicability predicate and implementation. A **RulePatch** groups rules for a feature. The **Rulebook** façade mediates invocations and patch loading, with unloading optional. Queries, change requests and notifications cross the economy/host boundary. The authors recommend keeping the economy's property model separate from an engine's other ECS uses.

An invocation finds applicable rules; conflict resolution chooses an ordering. Loading later rules is the simplest priority policy, while more complex games may define precedence explicitly. Rules can therefore add behavior for new data types or operations, and replace or compose with existing behavior. This is a concrete alternative to scattering conditional exceptions across operations. Its scope depends on routing the relevant accesses through the rule engine and correctly specifying applicability, precedence and composition.

Pages 7–9 demonstrate a simplified *Magic: The Gathering* sequence: creature properties, damage, lethal damage, indestructibility and destruction. New patches override the lethal-damage decision and add destruction behavior without editing previous patches. This preserves a positive modularity example. The example deliberately simplifies damage handling and does not establish arbitrary feature independence, semantic noninterference, live code replacement, migration of pending work or external-effect rollback.

## What the evaluation reports

Page 9 describes two student-course quasi-experiments using Lua and LÖVE. Each team develops a real-time tower-defense game and a turn-based RPG. Genre order is split across teams, but **every team uses free design first and the supplied Rulebook implementation second**. Table I is called a Latin Square; the architecture treatment remains confounded with project period. The paper does not report random assignment, raw responses, team count for the main course, effect sizes, uncertainty intervals or significance tests.

| Evaluation component | Reported result and usable scope |
| --- | --- |
| Pilot: six students in two teams, previous architecture iteration, summer course | Useful architecture with a steep learning curve; observations informed the next course. Not six independent project comparisons or a replication of the identical implementation. |
| Main course: 25 undergraduates and three graduate students, mostly computer science | Preliminary implementation effort and perceived usefulness are inconclusive. This wording is not a statistical equivalence finding. |
| Architectural change burden | Authors report slightly fewer changes to the game architecture. Preserve the favorable observation; no numerical magnitude or independent change-log measure is supplied here. |
| Willingness to reuse | Almost all students reportedly would use Rulebook again. Positive stated preference is distinct from actual later adoption or measured net maintenance benefit. |
| Proofs of concept | The extended card example is reported to handle overriding mechanics successfully. A Ruby Dungeons & Dragons fifth-edition simulator is ongoing; neither is a controlled industrial comparison. |

Both projects receive equal nominal time. The second coincides with finals and other deadlines and receives lower grades; the authors attribute difficulty to overload, but the design does not isolate that cause from architecture, task or learning effects. Small game scope and a continuing learning curve limit transfer. Examples reportedly help, while understanding the rationale demands software-design knowledge.

The supplied initial economy implementation excludes its construction effort from the comparison. Thus the study does not estimate total adoption cost or lifecycle savings. Page 10 explicitly describes the evaluation as incomplete. The conclusion's broad language about reducing development cost must be read alongside these preliminary outcomes, not used to replace them.

Runtime cost is a material adverse consideration. Page 10 reports that straightforward implementations can suffer rapidly growing, described-as-exponential cost when conflicting rules invoke further rules. This is an author diagnosis, without a benchmark curve or complexity proof in the paper. Conflict ordering and caching are left as performance research. Proposed professional interviews, larger game work and refactoring a preexisting open-source game are future activities in this edition, not completed evidence.

The inspected code makes several boundaries concrete:

- [`rulesolver.lua`](https://gitlab.com/unlimited-rulebook/ur-proto/-/blob/3c6f423a74690a8566c042d2bb56fa2150652b23/rulesolver.lua) gathers cases, checks predicates, and orders conflicts using another invocation of the `precedes` rule. It builds the final function using `compose`/`super`; otherwise a higher-priority implementation replaces the accumulated one. This supplies a direct structural route for nested dispatch overhead.
- [`rules/common.lua`](https://gitlab.com/unlimited-rulebook/ur-proto/-/blob/3c6f423a74690a8566c042d2bb56fa2150652b23/rules/common.lua) implements default precedence through rule-entity IDs. The damage example overrides precedence for a description rule. Priority is programmable, not a fixed proof that overlapping rules agree.
- [`init.lua`](https://gitlab.com/unlimited-rulebook/ur-proto/-/blob/3c6f423a74690a8566c042d2bb56fa2150652b23/init.lua) and `entity.lua` store accessible `record` fields. Predicates and implementations close over the same mutable Record. Encapsulation and predicate read-only behavior are design conventions in this inspected prototype, not an enforced capability or effect discipline.
- [`record.lua`](https://gitlab.com/unlimited-rulebook/ur-proto/-/blob/3c6f423a74690a8566c042d2bb56fa2150652b23/record.lua) stores mutable property tables and shallow-copies defaults. `new_property` replaces that property's storage table. Reinvoking it for an existing property would therefore discard that table's prior entity entries; this is a static consequence, not an observed reload experiment. The source does not justify treating arbitrary rule/property reload as state-preserving migration.
- The [released damage rule](https://gitlab.com/unlimited-rulebook/prototype-example/-/blob/f51d8ba7eecf122137957dba4ab2c21866f14bc4/rules/damage.lua) accumulates damage, while the paper's simplified example assigns the latest amount. This is an explicit example difference, not a silently substituted publication result. Scenario 05 sets up a counter-bearing indestructible creature against a creature with wither; reading that setup does not execute its outcome.
- Ruby's inspected solver also orders applicable cases through `precedes` and composes implementations. Its TODO retains substantial unfinished game features. Three files do not establish the simulator's overall completeness or performance.

The prototype README links the two 2019 course project templates. They are retained access leads, not acquired evaluation data. The present file set contains no newly inspected participant instruments or responses.

## Consequence for Nu and the next reading

S269 supplies an implemented, game-specific architecture for localizing self-modifying economy rules, favorable example behavior, a modest reported change-burden benefit and strong reuse preference. The inconclusive effort/usefulness findings, learning cost, excluded initial effort and dispatch overhead remain equally part of its evidence. Its presence in S268's industry-scale review does not turn its student courses and small demonstrations into industrial comparative results.

Together with [S225 Micro-Machinations](S225-micro-machinations-adaptation.md), it narrows broad novelty claims around separated game-economy models and changing mechanics. Their actual contracts differ: S225 applies named deltas between steps and explicitly resets redefined pools; S269 selects/combines rules over a mutable property store. Neither mechanism alone establishes Nu's claimed advantages, an immutable history, preservation of pending work, or net professional/agent maintenance benefit. D1's explicit enumeration versus equivalent catch-all remains a different source treatment; rule predicates are not that control.

## What the merge preserves

Sections 3–4, pp. 3–6, model the level as a labeled directed acyclic graph. Nodes have unique IDs and single-valued properties. Direct dependency edges propagate parent changes to children; indirect edges represent references without that propagation. Assets have graph identities/references, while their internal mesh, texture and code contents are delegated to suitable external merge methods. This is a representation and integration contract, not a proof that arbitrary script behavior is captured by the graph.

| Step | Primary rule | Consequence |
| --- | --- | --- |
| Identify changes, p. 3 | Compare local and remote graphs with a common ancestor, using unique node IDs. Classify nodes as unchanged, added, deleted or modified; a changed direct parent also marks its dependent node modified. | Identity must survive serialization and branches. The paper does not reconstruct ID generation/collision handling or infer semantic identity after arbitrary copying/reorganization. |
| Add/delete, pp. 3–4 | Insert added nodes and connect their direct parent, or scene root. A deletion conflicts with concurrent modification of the node or affected subtree; surviving subtrees are reconnected as described. | Deletion is checked through dependency structure, beyond independent text lines. |
| Modify/conflict, p. 4 | Merge changes to different properties; concurrent changes to the same property conflict. Users can edit the partially merged scene or prefer one branch automatically. | Automatic completion can deliberately discard edits. Structural validity does not establish retention of both users' intentions. |
| Remove cycles, p. 4 | After merge/conflict resolution, drop a lowest-height indirect edge in a detected cycle, or a direct edge when necessary. | Acyclicity is restored by changing dependencies. The prose does not fully specify ordering/tie handling for a cyclic intermediate graph; no implementation or formal proof was inspected. |
| Handle code/assets, pp. 3–5 | Use asset-specific merge methods; publish code to the shared main repository only when it compiles, retaining intermediate versions separately. Keyframed animation merging is explicitly unsupported. | Compilation is an admission check, not an oracle for retained gameplay, temporal obligations or script/reference completeness. |
| Apply the result, pp. 4–6 | Parse Unity 5 serialized scenes into the graph, merge, serialize a new scene and reload through an editor plugin. Colored indicators show others' object/asset edits. Synchronization is configurable; tests use roughly ten seconds. | Reloading locks the Unity interface while caches refresh. The measured merge time is not the whole transfer/reload interruption. |

The decisive live-state boundary is explicit at the end of §4: **synchronization stops in simulation/play mode**. Sharing edits while users play is proposed future work. “Playable after merging” therefore does not mean preservation of an active heap, timers, in-flight events, external effects or current play session. This is a useful scene-authoring alternative to compare with Nu's actual source-grounded state contract, without erasing its narrower contribution.

Figure 4 also has an internal branch-label inconsistency: its caption says A deletes the object and B modifies it, then claims that preferring A leaves the object present; the displayed merged image retains the blue object. Preserve the conflict example without treating that caption as an unambiguous test of the branch-selection rule.

## Measured feasibility and comparative outcome

Section 5.1 and Table 1, pp. 6–7, report an unoptimized Python implementation on a 2.6 GHz desktop. Four selected scenes were playable before and after merging, with automatic preferred-branch conflict handling and no manual intervention. This is positive feasibility evidence, not preservation of every edit or an independently checked behavioral specification.

| Scene | Ancestor MB | Ancestor nodes / edges | Diff A / B nodes | Merged nodes / edges | Merge seconds |
| --- | ---: | ---: | ---: | ---: | ---: |
| Room | 205 | 79 / 84 | 168 / 85 | 244 / 248 | 0.07 |
| Planets | 149 | 2702 / 3352 | 545 / 31 | 2184 / 2710 | 0.80 |
| Lab | 3172 | 2800 / 3156 | 131 / 303 | 3142 / 3498 | 1.40 |
| Vikings | 1620 | 2249 / 2318 | 361 / 467 | 2384 / 2452 | 6.16 |

Vikings uses approximately 1.5 hours of editing per branch, a different workload from ordinary frequent synchronization. Table 1 and §5.1 give the values above; the introduction instead summarizes 205–3172 MB and 0.07–0.92 seconds, which omits the smaller Planets size and understates later timings. No repetitions, variance, network transfer time or complete reload-time measurement is supplied. The claim that manual merging would take unreasonable time is an author judgment, not a timed manual baseline for these four scenes.

Section 5.2, pp. 6–7, describes **nine recruited users: seven experts and two novices**, in groups of two or three without mixing categories. “Expert” means a game-jam win, a game-design publication or a published app-store game; the two novices are 3D artists with at least four years of company experience. They are novice Unity users, not novice professionals. The introduction instead says **six users, three expert designers**; no reconciliation or participant-flow account is supplied. Do not add the two counts or silently choose a field-study population.

Both conditions involve cooperative editing of a supplied small playable scene: LevelMerge versus Git text merge with manual conflict resolution. Four guided tasks deliberately elicit addition, hierarchy, semantic and deletion conflicts; a roughly half-hour open task requires adding a script. Each task has two repetitions, one per merge workflow, with randomized presentation order. The session lasts 1.5 hours plus training/final survey. Talking before/during tasks is forbidden; users are not told what changes between repetitions. Direct scene-file repair, reverting, skipping and declaring an unrecoverable task are allowed.

Users rate difficulty from 1 (hard) to 5 (easy). The analysis adds **0 for a blocked task or a revert that loses all edits**. Reported means are **4.11 for LevelMerge versus 1.85 for Git**, and Git corrupts **23.6% of scenes**. These are favorable observed results under intentionally conflict-prone tasks. The mean combines perceived ease with failure/reversion status; it is not an ease score conditioned only on successful tasks, a time saving or a validated interval-scale effect. Raw counts/denominators, per-task/group results, uncertainty and an inferential test are absent. Do not reverse-engineer the 23.6% denominator, infer zero LevelMerge failures from omitted counts, or interpret the introduction's “significantly” as a reported statistical test.

Almost all users notice the difference, and qualitative feedback favors collaboration and avoiding corrupted scenes. Some find the activity indicators insufficiently visible and want per-attribute awareness. Preserve this positive practical evidence and observed UI cost. It neither establishes production prevalence of the designed conflicts nor net maintenance benefit across a game's lifecycle.

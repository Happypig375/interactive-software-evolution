## Update boundary and synchronization

Adapt.Net treats a component as a runtime object graph rooted at one main object. Fields contain both internal references and connection references; external interaction is supposed to pass through public component interfaces. XML configuration descriptions and adaptation profiles select parameter, connection, placement or implementation changes. An aspect introduces `IConfigure`/`IUpdate` behavior at the component root, using reflection during reconfiguration rather than on each functional call. **Source locators:** architecture and component boundary, PDF pp. 1–4 and Figure 1; synchronization/proxy excerpt, PDF pp. 4–5 and Figure 2.

The paper summarizes an earlier connection-blocking protocol: affected calls acquire read locks; reconfiguration acquires write locks in a calculated order and waits until no method is executing on the affected components. The full order/quiescence algorithm is delegated to reference 2. Figure 2's aspect proxy intercepts root calls, invokes the current instance before an update and forwards to `target` afterward. `UpdateReference` acquires the writer lock and replaces `target` with the return value of object-graph migration. The authors state that reader-writer locks support nested/recursive calls and that arbitrary clients may retain copies of the original proxy because it remains the stable external indirection. Active components can have unchangeable stack references in their own threads, which is another reason for forwarding through that proxy.

These statements establish the intended update boundary, not a general atomicity theorem. The paper does not restate the blocking-order proof, define behavior for every application lock, or cover an external reference to an interior object that escaped the component boundary. Stack references are redirected only when later calls go through the proxy; the object already present on a stack is not transformed in place. The reported “reconfigurable state” is a precondition for the graph walk, while field correspondence, resources and successor invariants remain separate obligations.

## Assembly mapping, graph traversal, aliases and cycles

An update supplies an **assembly mapping** from deployed assemblies/types to successor versions. Starting at the component root, `UpdateObjectGraph` tests each object against that mapping. A mapped object is allocated with `.NET`'s `FormatterServices.GetUninitializedObject`: metadata/method tables and zero-initialized field storage are created, but no constructor runs. The old object's fields are then inspected. Primitive/leaf values are copied; object references are recursively traversed; and each returned old-or-new reference is assigned into the destination field. Unmapped objects are retained, while their reference fields can be rewritten to updated descendants. **Source locator:** §3.1 and Figure 3, PDF p. 6 continuing onto p. 7.

The authors describe field-wise copying as complete state transfer because they model object state as its fields. That is a premise of the mechanism, not evidence that files, sockets, timers, native handles, thread-local state, in-flight effects or other external resources migrate. Constructor suppression avoids constructor side effects, but it also bypasses constructor/field-initializer invariants. From the stated zero-allocation plus old-field-copy procedure, an added destination field that receives no mapped old value remains at its runtime default unless a special update handler repairs it; the paper does not present this as a schema policy.

The excerpt does not specify how `_updatedField` is found, what happens when a field is renamed, deleted or changes type, or whether incompatible `SetValue` calls are converted or rejected. It also omits a null-value policy despite calling `GetType` on field values, and gives no complete treatment of arrays, collection internals, static fields or readonly/invariant-sensitive members. Figure 3 is explicitly excerpted code, so these omissions are exact method gaps rather than evidence that every such case fails.

The naive recursion would loop on a cyclic graph. Figure 4 adds a per-update `visitedNodes` table keyed by a unique number from an `IDGenerator`. A first visit stores either the original object or its newly allocated replacement **before** its fields are recursively traversed; a later visit returns that stored reference. This is the paper's mechanism for terminating cycles and reinstalling the same replacement at repeated references. It can preserve aliases and cyclic back-edges within the traversed graph if the ID generator is unique/stable for each source object during that update and the table is correctly scoped. The paper does not define the generator, prove collision freedom, or address aliases held outside the traversed component graph. **Source locator:** Figure 4 and accompanying text, PDF p. 7.

Delegates receive additional treatment because they contain a target object plus method metadata. The paper says both parts are checked for updates, a successor delegate is created, and multicast delegates are traversed as collections of delegates. It gives no code because the handling is described as complex. This supplies an intended callback-correspondence mechanism, without a complete rule for overload/signature changes, removed methods, external targets or failed delegate construction.

**API correspondence checked during review:** PDF p. 7 specifically names `Delegate.Combine` for supplying a new target and/or `MethodInfo`. Microsoft's [Combine reference](https://learn.microsoft.com/en-us/dotnet/api/system.delegate.combine?view=netframework-4.8.1) accepts existing delegates, while [CreateDelegate](https://learn.microsoft.com/en-us/dotnet/api/system.delegate.createdelegate?view=netframework-4.8.1) supplies object/`MethodInfo` binding overloads. ## Windows Forms controls, events and native resources

Generic uninitialized allocation would preserve old control state but not automatically activate a successor layout. The Windows Forms update handler therefore constructs a **reference control** of the new version with its default constructor. After the generic graph transfer, it uses that instance as the template for location, font, colors, size, child-control structure and configured event handlers. Existing content remains from the old control; new child controls are added, missing ones removed and layout properties changed to match the reference control. The constructor is therefore deliberately used for the GUI template even though ordinary migrated objects bypass constructors. **Source locator:** §3.2, PDF p. 8.

Windows Forms events are backed by delegates and an event-list structure. The update handler uses reflection to balance the migrated control's keyed event list against the reference control: add newly configured handlers, remove absent handlers, redirect targets to the new proxy and adjust multicast-delegate content. This is more than copying field values. It also means successful GUI migration depends on framework-private event representation, key correspondence, reflection access and the handler reconciliation code. The paper supplies no independent test matrix for added/removed handlers, duplicate subscriptions, closure state or effects already scheduled by an old handler. **Source locator:** event reconciliation after Figure 5, PDF p. 9.

Figure 5 shows a native Win32 window retaining the original interwoven control proxy. After the first update, the authors say two proxies remain: the initial proxy receives native-thread/WndProc calls and forwards them to the latest implementation, while event delegates point directly to the latest proxy. This is a deliberate indirection around a native reference that is not migrated. It is not a generic native-resource-transfer rule; the paper does not discuss recreation/disposal of handles, graphics resources, timers or other external state. **Source locator:** Figure 5 and its explanation, PDF p. 9.

Controls may be manipulated only on their creator thread. Because the configuration manager normally runs elsewhere, the framework sets an update flag and defers the graphical update until just before the next functional call enters the component on the control's thread. A member continues to point to the initial proxy as the graph root. The paper gives no bound if no qualifying call arrives, no account of messages/effects between the request and deferred installation, and no explicit completion signal separating “requested” from “installed.” **Source locator:** end of §3.2, PDF p. 10.

## Failure, rollback and measured-cost limits

No transactional rollback procedure is described. Figure 2 gives `UpdateReference` a Boolean result and writer-lock timeout parameter, but the displayed excerpt has no false-return branch, catch block, timeout disposition or recovery path. The recursive algorithm can rewrite fields of retained objects while allocating replacements, and GUI post-processing mutates control/event structures. The paper does not say how those changes are undone after a failed reflection assignment, missing type/member, constructor/update-handler exception or partial delegate reconciliation. Publication of a new root through `target` occurs after `UpdateObjectGraph` returns, but that alone does not establish rollback of mutations to retained shared nodes or external/UI state.

The paper contains **no performance experiment, comparator workload, sample count or denominator**. It qualitatively claims synchronization overhead of roughly one atomic instruction or one-to-two instructions for normal calls, plus one generated virtual forwarding call after update. It supplies no timings, hardware, graph sizes, update duration, blackout distribution, memory cost, reflection cost, GUI workload or end-to-end comparison. Section 5 explicitly says evaluation will appear in a future publication because optimization is ongoing. These claims therefore remain implementation expectations/experience, not measurements. **Source locators:** overhead prose, PDF pp. 4–5; future-evaluation statement, PDF p. 11.

## Consequence for R10 and the background method

S219 resolves S218's selected state-transfer dependency with a constructive object-graph method: assembly-directed type replacement, recursive reference rewriting, alias/cycle memoization, delegate repair and a Windows Forms/native-proxy special case. It also exposes the required assumptions: a quiescent component boundary, controlled root references, compatible field/member correspondence, stable per-update object identity, framework-specific handler access, successful constructor/template behavior and an installation/recovery policy that the paper does not supply.

This is a useful contrast for **R10**, but it is not the same mechanism as Nu/Prime conversion. S219 walks a live mutable object graph, maps runtime types by assembly, preserves graph topology through an identity table and repairs selected delegates/controls. Prime serializes a model to symbolic values and reconstructs a destination value by name/position/type rules, with defaults and an application fallback. A positive result for one cannot certify the other's field correspondence, aliasing, callbacks, native resources, synchronization or rollback. Their shared lesson is narrower: type-valid/default-initialized state and installed behavior are different outcomes, and constructors, new fields, callbacks and external resources require explicit correspondence and observations.

The paper does not establish Nu-specific novelty, runtime feasibility or benefit. It offers no human/agent maintenance comparison and no measured case for avoiding reconstruction. Any later R10 use should charge mapping, synchronization, handler/native reconciliation, deferred installation, validation and recovery, while preserving failed/partial outcomes. No experiment or Nu source change follows from this reading.

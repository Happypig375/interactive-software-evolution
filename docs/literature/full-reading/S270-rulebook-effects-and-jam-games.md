## What changed from the conference architecture

Pages 1–3 derive the pattern from the broader Unlimited Rulebook programme: ProSA-RA, a literature review, professional interviews, grey literature, proofs of concept and the earlier course study. The thesis contains 33 architectural requirements. These are research/design inputs, not a new independent intervention merely because this publication summarizes them.

The refined mechanism represents an intended simulation operation as an **Effect** object. **Rules** inspect the effect and current **World**, then amend the effect, resolve it into state changes, or generate further effects. The **Rulebook** locates and invokes applicable rules; an optional **EffectStream** holds pending effects. Rules may be permanent or associated with changing simulation elements. This separates a request for an operation from the actual behavior after currently active mechanics intervene.

The pattern assumes simulation state is behind an abstraction and relevant state changes pass through effect resolution. The authors explicitly warn that partial adoption can cost more than retaining the existing design, and that changing the pattern's implementation later is itself a project risk. It does not require the earlier prototype's particular mutable property-store implementation, nor an immutable world.

The caravan example introduces ruins that slow movement and shelter stationary activity from rain. One rule tags movement-related effects, another adjusts their duration, and another cancels a chained soaking effect based on its predecessor. Algorithms 1–2 make the intended reduction in scattered edits concrete. The tagging rule still has to recognize the relevant effect kinds; the pattern does not infer the meaning of arbitrary future operations.

Pages 4–6 distinguish rule storage, matching and conflict policy. Candidate optimizations use spatial filtering, effect types or predicate indexing; these are design alternatives, not measured speedups here. Noncommuting rules require ordering because earlier changes can alter later applicability. Reconsidering earlier rules after effect changes can help, with per-rule/per-effect guards against repeated handling. That guard alone does not prove termination for an unbounded stream of newly created effects.

The **Amend–Resolve–Chain (ARC)** variation orders three roles: amend effect data, resolve state changes, then schedule subsequent effects. Preview runs only amendment rules, making the resulting effect easier to interpret without committing its resolution. The authors call this a useful convention and explicitly deny universal applicability. It supplies neither an all-rules commutativity proof nor a guarantee that a later action sees the state used for its preview. Shared effect/world memory makes parallel rule execution a future problem.

The authors ground the pattern in Plotkin's Inform7 work and Bucklew's Caves of Qud/Sproggiwood practice. They distinguish its game-simulation guidance from ECS, Command, Chain of Responsibility, Decorator, Observer and Blackboard. These are explicit predecessors and compositional relationships; their mention is not a newly completed reading of the underlying talks or systems.

## Case method and actual outcomes

Pages 6–9 describe a qualitative, interpretive case study of three open-source jam games the authors helped develop. Selection requires Rulebook use, sufficient completion, source access and preferably an accessible design process. Questions concern motivation, implementation decisions and architectural consequences. Source inspection and participant knowledge inform the account; no non-Rulebook control, randomized treatment, timed change dataset or measured lifecycle saving is reported. Team sizes must not be summed into a count of unique independent participants.

| Case and setting | Favorable evidence | Costs and limits preserved by the authors |
| --- | --- | --- |
| **Legend of Slime:** Crossover Jam 2021; four-person team, 48 hours, Godot 3.3, puzzle game | Component-level rulebooks support power combinations and more than a dozen puzzle mechanics, with a complete sequence of stages. Rule grouping helps runtime addition/removal. | Familiar component design limits learning overhead. Two map operations need special handling; pairwise power combinations duplicate code. Conventional per-effect abstract methods might achieve similar results for the predominantly single-entity interactions. |
| **Dungeon Architect:** Ludum Dare 50; four-person team, 72 hours, Godot 3.4, base-building game | A central rulebook lets room mechanics affect other objects. Developers report spending less effort on interactions and more on polish, and attaining acceptable gameplay length. | Only two effect types are needed; most room rules are unique, limiting reuse. No ARC or effect-stream mechanism is used. The effort account is qualitative. |
| **Honey BZZZness:** Ludum Dare 53; seven-person team, 72 hours, Godot 4.0, mobile clicker | Amendment/resolution separation supports reusable transaction calculations and previews of action cost; the team reports avoiding rule-conflict complications. | Steeper learning, misunderstandings and scattered state access cost time. A substantial UI and mechanics scope leave the game barely finished with many features omitted. The suggestion that it would be less complete without Rulebook is the authors' counterfactual interpretation. |

All three cases use JSON-like effect values. The team considered stronger typing too costly in boilerplate for the jams; this is situated design reasoning, not a controlled typing-cost result. None of the jam games relies on the proposed effect-stream/chaining mechanism; synchronous nested resolutions do occur. This distinguishes the implemented cases from the full architectural vocabulary.

The authors report localized additions for unplanned mechanics and small central dispatch implementations, about 4–15 core lines. This is useful implementation simplicity under the chosen counting boundary; it excludes effect definitions, rules, game state, UI integration, learning and later rework. An unforeseen need to access state outside a cohesive module still required changes in multiple places.

The paper acknowledges expertise, direct participant/researcher involvement, the one engine family, three genres and short project scope. Longer maintenance might require revisiting decisions accepted as jam workarounds. These limits qualify transfer without erasing the demonstrated mechanisms or favorable experience. The later paper adds situated cases; it does not replace S269's inconclusive quantitative course findings with a controlled net-benefit estimate or a runtime benchmark.

The inspected contracts support the following source-located inferences:

- **Grimoire:** [`EffectSolver.gd`](https://gitlab.com/uspgamedev/grimoire-ars-bellica/grimoire-ars-bellica/-/blob/ddcf738cffe0598799773d7e382c379f7917d989/gameplay/effect/EffectSolver.gd) walks a linked effect sequence and restarts processing when the current effect object is replaced. Preview sets a flag and processes effects without invoking the resolution phase. It mutates supplied effect data; it does not snapshot the whole world. `Rule.process_effect` records handled effect identities until solver cleanup. The application phase calls `_apply_effect` directly, so the separate public `apply_effect` guard is not the enforcement path used there. No general termination or once-only-external-effect guarantee follows from the illustrated guard.
- **Legend:** [`Entity.gd`](https://github.com/uspgamedev/crossover-slime/blob/771c6e24735c5b5b60fd084e4e5ff459dd922efd/entity/Entity.gd) dispatches through reversed child order and checks cancellation before each handler. `Stage.gd` treats splash and wall-blocked movement specially. Fire and water scripts both contain the compatible-power rewrite, supporting the reported duplication. Water effects and flood fill also use Godot timers; the game's pending work is broader than a synchronous rule call.
- **Dungeon:** [`Rulebook.gd`](https://gitlab.com/uspgamedev/ld50/-/blob/8819226e7799121b2e6876b63979030814e89e3a/dungeon/rule/Rulebook.gd) dispatches through effect-specific scene groups. The two enum tags select room-duration and room-connection calculations. The treasure rule adds its modifier when an adjacent challenge exists. The short solver body depends on surrounding rule registration, data and host access.
- **Honey:** [`rulebook.gd`](https://gitlab.com/uspgamedev/jams/ld53-clicker/-/blob/1859cbde1f323e5eec5ebfca7583dbf026addf82/gameplay/rulebook/rulebook.gd) processes modifier and application groups in that order. Cancellation is checked after each group, permitting rules within a group to shape the effect. Preview visits only modifiers. Both receive mutable `GameState`, so the phase split is not a static purity discipline. [`expand_button.gd`](https://gitlab.com/uspgamedev/jams/ld53-clicker/-/blob/1859cbde1f323e5eec5ebfca7583dbf026addf82/gameplay/hud/hive/expand_button.gd) creates a preview effect each frame, reads its amended wax cost and creates a new effect on click. It reuses rule logic without reserving the previewed state or ensuring a later value is identical.
- Honey's unlock rule sets a `bee_unlocked` trait; the lock rule reads it and may mark the effect prevented. These rules still need an appropriate order within the amendment group. ARC's broad phase order alone does not settle every such dependency. This is a static obligation, not a reproduced unlock defect.

## Nu relevance and next consequential action

S270 supplies an implemented alternative for separating requested operations, current-rule amendment and committed state changes, with useful preview and localized extension experience. Compare that actual contract with Nu's state/effect and integration claims, S225's live model deltas/reset policy, and S269's predicate-dispatch prototype. Neither effects-as-data nor an ARC diagram alone establishes persistent history, arbitrary source-edit migration, pending-timer preservation or rollback of host effects. S269's nested priority-dispatch problem is addressed here through simpler design alternatives and acknowledged tradeoffs, not a measured universal performance solution.

The observed positive and adverse cases support conditional architectural guidance: expected cross-cutting mechanics, state access, team familiarity, preview needs and rule order matter. Nu-specific net value remains empirically unknown. Read the **2021 thesis** next, after native registration, for the original course instruments/outcomes, professional interviews, 33 requirements and later-iteration lineage. Its detailed methods remain a primary-reading gap; unknown Nu benefit is a separate question. Larger independent commercial evaluations and optimized rule processing are future work in this accepted edition, not findings that this reconstruction can supply.

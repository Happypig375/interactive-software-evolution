## Method and useful contribution

Sections2–4, pp2–3, adapt prior problem categories, including [S249](S249-game-postmortems-155.md), and iteratively extract problem quotations from postmortems' negative sections. Each author initially picks20 reports randomly, discusses types and revisits affected coding. Later selections balance years manually; reports lacking useful process information are discarded. Stopping when no new type appears concerns category saturation, not a representative probability sample or absence of other industry problems. No initial sampling frame, complete rejection flow or independent reliability statistic is supplied.

The reported200 games have1,035 coded problem entries in20 types and three groups. A quotation is stored with report/game identity, year, source URL, platform, genre, mode and category. Multiple platform/genre/mode values are allowed. The move from JSON/schema to one-row-per-problem CSV makes selected evidence traceable and amenable to passive counting. The public repository permits reviewed contributions, explicitly making it an evolving dataset.

The taxonomy separates production (design, documentation, tools, technical, testing, bugs, prototyping), management (scope, feature creep/cutting, delay, crunch, communication, team, budget, concurrent projects, planning, security) and business (marketing, monetization). This is useful for specifying the scope of a Nu claim. Reducing one source-edit burden does not automatically address staffing, marketing, asset production or the intended player experience.

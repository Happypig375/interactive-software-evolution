## Event representation, propagation and blocking

**Primary locators:** JEScala forms and synchronicity, Chapter 4 §§4.1–4.4, Figures 4.1 and 4.9–4.10, printed pp. 92–105 / PDF pp. 93–106; event-graph traversal and dynamic deployment, Chapter 7 §§7.1–7.1.2, Figures 7.1–7.2, printed pp. 140–142 / PDF pp. 141–143; disjunction queues, blocking and optimizations, Chapter 7 §§7.3–7.3.1, printed pp. 143–145 / PDF pp. 144–146.

JEScala extends EScala's object-member events with asynchronous occurrences and explicit Join-style disjunctions. A primitive event is imperative or implicit. Imperative events declare `sync` or `async`, with synchronous default. Implicit before/after events observe an exposed method without inserting an emission at its call site and have synchronous and asynchronous variants. Declarative events build graphs with union, map and filter; they propagate the triggering occurrence's synchronicity unless `!!` forces asynchronous handling. Abstract events cannot fix synchronicity because an implementation may be primitive or composed. A union can therefore deliver synchronous and asynchronous occurrences through the same event identity.

An event graph is a directed graph rather than necessarily a tree: a composed node may feed several later expressions. Triggering a primitive event performs a depth-first traversal of the active graph. Nodes transform or filter the occurrence and collect direct and indirect handlers as zero-argument reactions. JEScala executes those reactions only after collection, avoiding mutation of the current reaction collection during handler execution. Registration enables paths from a source to the new observer; removing the last observer disables nodes that no longer lead to a handler. This is an implementation optimization, not automatic application-lifecycle cleanup.

Synchronous triggering uses the caller's thread and returns after the reached handlers return. The guarantee is bounded: a handler may start asynchronous work that outlives its return. Asynchronous triggering collects on the sender thread and, if any reactions remain, schedules their execution on another thread. Several occurrences can traverse the graph concurrently, so handler lists and per-occurrence reaction buffers require protection. The implementation first created short-lived threads and then added pooling; pool occupancy can defer work, and neither mode supplies a latency bound.

A disjunction owns one queue for every observed event. An unmatched occurrence stays in its event's queue. If one pattern becomes complete, its occurrences are removed atomically for that disjunction and its result event fires. If several patterns are complete, one is chosen randomly. The author treats Scala's random selection as a fairness mechanism; no starvation bound, deadline guarantee, deterministic replay rule or fairness proof is supplied.

An unmatched synchronous occurrence stores its arguments and blocked delivery thread. That caller resumes only after its occurrence participates in a pattern and all handlers reached from the result event have returned. When a match includes one or more synchronous occurrences, §7.3 says the implementation uses the waiting thread of the **“syntactically first event of the pattern”** to execute the result reactions. It motivates this syntactic choice with same-thread libraries. A match containing only asynchronous occurrences runs via an asynchronous worker. Queue insertion is normally deferred as a collected reaction so that a synchronous occurrence does not block traversal before the other reachable reactions have been found.

The syntactically-first waiting-thread rule and random selection statement are in §7.3, printed pp. 143–144 / PDF pp. 144–145. Chapter 4 §4.4.3 says a matched result is synchronous when **at least one** participating occurrence is synchronous and permits occurrence-dependent synchronicity (Figure 4.10, printed pp. 104–105 / PDF pp. 105–106). Neither passage says that the first syntactic position must be synchronous or defines the mixed case in which an asynchronous occurrence occupies that position and a later one is synchronous. Reading “syntactically first event” as the first synchronous participant is a plausible implementation inference because only synchronous arrivals store waiting threads, but it is not a verified rule; the source archive remains unavailable.

Three optimizations narrow this cost. A thread pool reuses workers. An asynchronous source observed only by disjunctions can enqueue during collection and avoid a separate enqueue reaction. A nullary event promised to be always asynchronous can use a counter instead of queued argument/thread records. The final optimization depends on the programmer calling `markNullaryAsync`; a later synchronous arrival raises a runtime exception. The dissertation proposes future analysis rather than claiming the promise is statically verified.

The `markNullaryAsync` promise and runtime-exception behavior appear in §7.3.1, printed pp. 144–145 / PDF pp. 145–146.

The model therefore exposes several obligations that the compact syntax does not discharge: pure map/filter functions if propagation order should not affect state; correct sync/async choices; re-emission of persistent state tokens; safe dynamic registration/removal; bounded queues; and avoidance of cycles of blocked synchronous occurrences. The conclusion explicitly calls mixed synchronous/asynchronous events and deadlocks challenging and leaves a formal account of occurrence-dependent synchronicity for future work.

## Finite-state descriptions and implementation alternatives

**Primary locators:** DSL definition, inheritance and implementation alternatives, Chapter 5 §§5.4–5.5, Figures 5.9–5.11 and 5.16–5.19, printed pp. 115–127 / PDF pp. 116–128; generated Join, hash-map and array implementations, Chapter 7 §7.4, printed pp. 145–147 / PDF pp. 146–148; code-size formulas and triangle benchmark, Chapter 8 §8.4, Figures 8.7–8.9, printed pp. 162–165 / PDF pp. 163–166.

The dissertation makes the finite-state-machine construction more explicit than S142. A transition description has source state, destination state and a nullary action event, with an optional reaction or event trigger. `initialState` freezes the mutable transition collection, derives state/action sets, asks the selected implementation layer to build its structures and injects the initial state. A subclass may call `unfreeze`, remove or add transitions and freeze again. For the Join implementation, already-generated disjunctions cannot be extended: the superclass structure is disabled and replaced. This is reconstruction under an inherited description, not an in-place proof that arbitrary active state and queued work survive a revision.

The same description can select three implementations:

- **`FSM_J`** generates asynchronous state events, a binary Join pattern for each transition, result-event unions for destinations and handlers that emit the next state token. It retains the general event/Join costs.
- **`FSM_N`** keeps a current-state variable, queues action events and uses a hash map as the transition function. When several waiting actions are valid, it randomly selects one.
- **`FSM_E`** enumerates states and actions and replaces the hash map with a two-dimensional transition table.

The direct implementations preserve the intended behavior of the generated Join state machine only under the stated restricted domain. The DSL accepts no arguments for action or state events. The dissertation's mouse-drag example needs position-carrying events, and its reader-writer lock needs an integer-valued reader-count state to avoid a fixed upper bound. Those are lower-level JEScala encodings, not cases covered by the DSL. The reader-writer listing around Figure 5.19 also switches between names such as `writeState` and `write`, and its displayed decrement branch is unclear at the one-reader boundary. That is a printed-listing inconsistency, not a reproduced program fault.

The argument-carrying alternatives and reader-count boundary are in §5.5 and Figures 5.16–5.19, printed pp. 123–127 / PDF pp. 124–128; Figure 5.19 is printed p. 127 / PDF p. 128.

For a description with `S` states and `T` transitions and no reactions, the dissertation derives `4 + S + T` lines for the DSL and between `4 + 2S + T` and `4 + 3S + T` for generated Join-style source, depending on incoming-edge structure. This is a syntactic formula. It does not measure authoring, debugging, review, representation conversion or later maintenance.

## Event monitors and their guarantee boundary

**Primary locators:** motivation, synchronizer design and limitations, Chapter 6 §§6.1–6.2, Figures 6.3–6.5, printed pp. 132–137 / PDF pp. 133–138; actor-backed implementation, Chapter 7 §7.5, printed pp. 147–148 / PDF pp. 148–149; evaluation, Chapter 8 §8.5 and Figure 8.10, printed pp. 166–167 / PDF pp. 167–168.

Ordinary JEScala handlers can mutate shared state concurrently. The event monitor groups selected handlers so they execute sequentially while the original event sender remains unblocked. The implementation's `Synchronizer` is a Scala actor. For each observed event it registers an asynchronous forwarding handler, sends the occurrence and a per-event identifier to the actor, then has the actor trigger a typed synchronous proxy event. Handlers register with that proxy. Because the actor processes one message at a time and waits for the synchronous proxy's handlers to return, handlers in the group do not overlap.

This differs from putting `synchronized` around each handler: separately supplied handlers do not have to agree on a lock object, event senders do not wait for the protected work, and one actor worker replaces a collection of blocked handler threads. It also differs from a general actor protocol because observed events and handlers remain dynamically registerable and have heterogeneous parameter types; identifiers and casts recover erased types inside the synchronizer.

The guarantee is local to synchronous execution of the registered proxy handlers. A handler can start asynchronous work and thereby escape serialization. The mechanism has no wait/notify equivalent, and exception behavior is listed as a limitation. Code that relies on the blocking completion of a synchronous handler needs additional synchronization after conversion to the monitor. The evaluation deliberately excludes such handlers. The event monitor therefore supports a scoped mutual-exclusion claim, not shared-state correctness, deadlock freedom, effect ordering beyond the group, resource cleanup or whole-program behavioral preservation.

## Evaluation and adverse evidence

The evidence comprises authored case studies and historical microbenchmarks, not a controlled maintenance study. Measurements used a two-core 2.66 GHz MacBookPro6,2 with 8 GB RAM, OS X 10.6.8, Java 6 and Scala 2.10. The implementation used for the experiments was a library without the chapter's proposed surface syntax; compiler integration and static analysis remained future work. No repetition count, warmup procedure, uncertainty interval or raw-data package is reported in the dissertation.

**Static case set.** The 34 rows are the same synthetic coordination set reconstructed in S142. JEScala is compared with **JL**, a restricted JEScala subset used as a direct encoding of a hypothetical Polyphonic-Scala style. It is not an independently engineered production comparator. The French summary reports aggregate reductions of **8% in source lines, 2% in event declarations, 54% in handlers and 61% in explicit event-triggering sites**. S142's checked row totals and exceptions remain the more informative record: event declarations rise in twelve rows, handlers rise in two, and one JEScala row has more source lines. The dissertation's “validity” wording does not convert these authored metrics into measured comprehension, fault, maintenance-time or extension benefit. **Primary locators:** §8.1 and tabular Figure 8.1, printed pp. 152–154 / PDF pp. 153–155; aggregate percentages in French summary §C.8.1, printed p. 216 / PDF p. 217.

A bounded row-level comparison finds all **34 numeric rows identical** to S142 Figure 8; only capitalization and the final row's contextual label differ (`Web Server (Chapter 4)` versus `Web Server (Section 2.3)`). The dissertation sums are therefore the same: JL/JEScala **2,764/2,532 LOC, 324/320 events, 223/101 handlers and 302/118 explicit triggers**. Reductions calculated from those totals are **8.39%, 1.23%, 54.71% and 60.93%**. Ordinary nearest-integer rounding would yield 8%, 1%, 55% and 61%. Unweighted means of the row-relative reductions are 8.83%, −5.26%, 46.91% (excluding the one zero-handler baseline) and 60.51%, so that alternative does not explain the French summary either. The source's 2% event and 54% handler figures are retained as reported but remain unresolved summary/table discrepancies; they are not substituted for the checked table arithmetic.

**Join and pattern benchmarks.** An elevator-like automaton compares JEScala, Scala Joins, Esper, JoCaml and C-omega. Dedicated-compiler systems lead the plotted throughput. The prose again says JEScala minimally outperforms Scala Joins while the plotted bar appears lower, so that small ordering remains a figure/prose discrepancy. Increasing both pattern and disjunction size from two to six reduces every system's normalized throughput. JEScala falls to about 25% of its own size-two baseline at size three and is then nearly flat. This does not compare equal absolute baselines or isolate expressivity from compiler/runtime differences. **Primary locators:** §§8.2.1–8.2.2 and Figures 8.2–8.4, printed pp. 154–156 / PDF pp. 155–157.

**Asynchronous-event optimizations.** A two-thread rock-paper-scissors benchmark runs 50,000 games. Pooling supplies the largest improvement; disjunction-only insertion and the nullary counter further improve the pooled case. Scala Joins is shown with and without a dummy parameter because that changes whether its own counter optimization applies. As S142 records, the favorable JEScala comparison is against the slower parameterized Scala-Joins case; the parameterless Scala-Joins counter remains faster in the plot. These bars do not establish a general performance advantage. **Primary locator:** §8.2.3 and Figures 8.5–8.6, printed pp. 157–158 / PDF pp. 158–159.

**Ray tracer.** The author manually ports a major part of a JoCaml ray tracer twice: once to a restricted “simulated JoCaml” JEScala style and once using implicit and declarative events. Both ports are single-VM: distribution is removed, client/server modules call directly, the scene is fixed rather than parsed, a shared image array replaces the original functional assembly, and initial image saving is omitted. Three extensions display progressive lines, save batches and broker requests to multiple servers while accepting only matching results. The restricted version requires inserted calls or component changes; the full JEScala version observes or composes existing/implicit events and is described as requiring no component modification. This is useful constructive evidence that implicit observation can externalize these particular extensions. It has no task timing, diff-size table, fault count, independent implementer, behavioral-equivalence test or distribution result. **Primary locator:** §8.3, especially §§8.3.1–8.3.3, printed pp. 158–161 / PDF pp. 159–162.

**FSM benchmark.** A three-state triangle processes a reproducible pseudo-random clockwise/counter-clockwise action sequence. At one million transitions, `FSM_J` takes about **37 seconds**, `FSM_N` about **3 seconds** and `FSM_E` about **0.3 seconds**. The general Join version needs a larger JVM heap for that run. The author calls the 0.3-second value only an indication because it is small. The optimized generated implementations beat the manual actor and state-pattern variants in this one benchmark. It supports the cost of replacing a general mechanism with a domain-specific transition function, not semantic equivalence for parameterized or effectful machines. **Primary locator:** §8.4.2 and Figures 8.7–8.9; the approximately 37/3/0.3-second interpretation is on printed p. 165 / PDF p. 166.

**Event-monitor simulation.** The author removes display and other I/O from an existing sequential EScala “universe” simulation, fixes a pseudo-random seed and creates a concurrent JEScala version that reuses sequential parts behind a synchronizer. At 5,000 steps, the plotted sequential version approaches **200 seconds** and the concurrent version is below **40 seconds**. Fixed pseudo-random input does not make the concurrent interleaving deterministic, which the text acknowledges. There is no no-synchronizer concurrent control, no equivalence distribution and no study of handlers whose completion is required by other handlers. The author predicts that a purpose-built concurrent version could be faster but does not test it. **Primary locator:** §8.5 and Figure 8.10; plot and interpretation on printed pp. 166–167 / PDF pp. 167–168.

## Consequences for B03, R05 and R13

S205 strengthens **B03** by separating four mechanisms that a generic “event system” label would conflate: non-consuming propagation through an event graph, consumption within each disjunction, caller blocking for synchronous occurrences, and serialization of a chosen handler group by an event monitor. It also shows that a declarative FSM description can support a much cheaper specialized implementation. The price is a set of boundary assumptions—nullary actions, explicit state-token discipline, random selection, correct synchronicity and monitor membership. This is constructive mechanism and scoped performance evidence. It does not establish lifecycle correctness, retained-world migration, external-effect compensation or a net maintenance benefit.

For **R05**, S205 suggests observations that would be necessary for any comparable coordination claim: occurrence order; which queue/group consumes an occurrence; sender and reaction thread identity; block/unblock horizon; handler-completion boundary; pending-queue growth; pattern selection under competition; registration/removal identity; and failure/exception behavior. The existing Nu stub-world feasibility result observes priority, `Resolve` and explicit unsubscription. Those facts do not make Nu a Join implementation or event monitor, and S205 supplies no Nu-specific oracle. A useful later comparison would have to bind the same interaction obligation and charge representation, instrumentation, synchronization and verification work.

For **R13**, implicit events and monitor proxies demonstrate ways to observe a method boundary or serialize selected reactions without inserting calls throughout participants. They do not prove that a replacement preserves the paddle block's input mapping, left priority, capture policy, clamp, state or effects. Handler grouping also cannot make downstream asynchronous work or host scheduling disappear. S205 therefore reinforces the existing distinction between typed/event-compatible wiring, local coordination and whole-program behavior; it does not add a theorem or justify promoting the simple key-remapping case by itself.

The remaining consequential gaps are concrete. The source and benchmark archives are still unacquired, so listing-to-artifact correspondence and reported timings are unreproduced. No formal semantics validates the occurrence-dependent sync/async model. No independent implementation or maintenance study tests the modularity claims. The event monitor does not cover blocking-dependent handlers or exceptional completion. These are evidence limits, not reasons to erase the positive compactness, extension and performance observations.

# S248 — Snowflake: safe manual memory, GC coexistence and workload tradeoffs

Matthew Parkinson, Dimitrios Vytiniotis, Kapil Vaswani, Manuel Costa, Pantazis Deligiannis, Dylan McDermott, Aaron Blankstein and Jonathan Balkind, *Project Snowflake: Non-blocking Safe Manual Memory Management in .NET*, PACMPL 1(OOPSLA), article 95, 2017, [DOI10.1145/3141879](https://doi.org/10.1145/3141879). Main-agent reading, 2026-10-04: **all 25 text/visual pages of the author-hosted PACMPL-formatted paper**, including ten figures, Table 1, examples and references. The explicitly linked, earlier **MSR-TR-2017-32** report additionally supplies **all Appendix A, pp25–40, text and visuals**, including Figures 11–38 and Tables 2–4. Its cover is inspected; its main pp2–24 are not independently fully reread. This is one primary work with a selected supplement, not an independent replication or an executed implementation.

Snowflake establishes a concrete alternative to wholly GC-managed allocation in .NET: selected objects have explicit ownership and guarded access, while their references into the ordinary GC heap remain traceable. Favorable cache and memory results coexist with slower workloads and longer individual GC pauses. Its contribution is a runtime/lifetime mechanism with measured tradeoffs, not persistent world history, live-code migration or a demonstrated Nu maintenance benefit.

## Ownership, access and the programming obligation

Sections 2–3, pp3–11, separate the GC heap from a manual heap in a **modified CoreCLR/CoreFX implementation using modified jemalloc**. An `Owner<T>` is a noncopyable value with a private unmanaged pointer. An object has one owning location, which can be on the stack or either heap; many threads can access that location. This is different from duplicating ownership. `Move` transfers ownership and clears the old location, abandoning an existing destination value if necessary. Owning child fields are abandoned recursively using recorded field offsets.

`Defend` installs protection in a thread-local shield slot and makes the object accessible through a `Shield<T>`. `Abandon` atomically removes the owner's pointer and queues the object for later reclamation. New protection cannot be acquired from that cleared owner; existing shields keep their protected accesses valid until released. Consequently, explicit abandonment is not necessarily immediate physical deallocation. Long-lived guards still retain their objects.

Shields are noncopyable, stack-only and passed by reference. Their cached value avoids repeated thread-local lookup during every object access, although protection operations themselves still use thread-local storage. Reusing a shield for a different object ends its old protection. Ordinary `using` disposal handles exceptional exit; it does not establish the application's correct lifetime or absence of leaks.

The paper explicitly shows that **the API alone is unsafe**. Its frontend rules must prevent owner/shield copying, prohibited by-value or generic uses, shield boxing or heap/closure escape, and references to manual objects escaping their shield lifetime. It describes conservative escape checking and an alternative heap-store check that throws on forbidden escape; detailed source-language/compiler treatment is deferred. No complete soundness proof, independently checked compiler or stock-current-.NET compatibility is established by this reading.

The array-backed list example changes allocation, resize, access and abandonment, using guards around manual spines while permitting ordinary GC elements to escape. The cache changes `Set` to accept an owner by reference and `TryGetValue` to populate a supplied shield. A removed cache entry can remain safely in use through an existing shield. These are real API and integration obligations, not merely an allocator switch with identical source.

Unique ownership cannot directly express arbitrary ownership cycles or shared ownership of persistent versions. The authors use a GC-resident `Manual<T>` wrapper when several references must reach one owner, at an additional allocation cost, and discuss a reference-counted extension. Heap-stored shields, cross-thread asynchronous continuation and finalizer policy remain open design issues. For Nu, retained roots, native resources, task handoff and callback lifetimes would each need an explicit mapping; none is supplied or tested here.

## Reclamation and the boundary with GC

Section 4.1, pp11–14, combines shield scanning, epochs and thread ejection. Abandoned objects enter thread-local deferred lists. A GC pause can collect a conservative Bloom-filter summary of active shields and reclaim unprotected entries; false positives can delay reclamation. Protection publication must not be suspended between reading an owner and publishing its shield, so the runtime coordinates this critical region with GC suspension.

The concurrent path uses global/local epochs and four list partitions. The displayed condition **object.epoch + 3 ≤ local epoch**, followed by an active-shield check, waits for enough epoch advancement before freeing an abandoned object. A prose sentence on p13 says “less than three epochs behind”; that wording conflicts with the displayed guard and surrounding reasoning. This note follows the explicit guard while retaining the static discrepancy. No implementation failure has been observed. Three logical epochs do not give a wall-clock reclamation deadline.

A stalled or blocked thread can be ejected from epoch agreement by protecting its shield page with `VirtualProtect`/`mprotect`. A later shield write faults, rejoins the protocol, synchronizes the epoch and retries. Existing guards still prevent their objects from being freed. The ejection path uses a try-lock, and rejoining waits for a lock. Thus the nonblocking reclamation contribution does not imply that every application operation avoids OS faults, locks or GC pauses. Weak-memory platforms also require the stated barriers; the x86 ordering assumptions are not universal hardware semantics.

Section 4.2, p15, places GC and manual allocation on opposite sides of virtual address **2^46**, extending one card table across both heaps. This preserves the ordinary write-barrier form. A trie marks manual object starts containing GC references; young collections combine dirty cards and the trie, while full collections scan all relevant manual objects. Manually managed objects can therefore remain GC roots, and manual allocation does not eliminate tracing work.

Section 6, pp18–20, makes the costs concrete. Manual roots are scanned synchronously even when the collector otherwise marks in the background. Removing bulky objects from the young heap can leave many more small GC objects to scan per collection. A resized manual array containing young references needs card marking. Jemalloc can allocate more slowly than the GC's bump allocator. In a controlled root-scanning example, sparse stores favor the trie by about13%; denser stores make it about10% or20% slower. These are specific traversal comparisons, not frame-tail measurements or a general bound on total GC overhead.

## Measured benefits and adverse results

The primary reports a 3.5GHz Xeon E5-1620 v3, 16GB RAM, Windows10 Enterprise64-bit, the authors' CoreCLR/CoreFX/jemalloc branches and **Workstation GC**. Its “8 physical cores” label is retained as reported, not independently verified here. Appendix A uses **32GB** for the large TPC-H dataset and describes Server GC results as preliminary, with several unstable configurations omitted. Peak working set is the OS process measurement, including both heaps and runtime metadata; it is not just live managed data or retained history.

Havlak is an additional appendix workload, not a seventh member silently added to the primary's six-benchmark scatter plot. Its construction phase allocates a large surviving graph; the later phase reuses pools. The authors attribute the unfavorable first phase to allocation throughput, manual-root card scanning and synchronous root processing. That explanation is mechanistically plausible and source-attributed, not an independently isolated causal experiment.

Appendix p26 prints a piecewise improvement formula whose two branches are both nonpositive: when GC peak memory is smaller, `1 − Manual/GC`; otherwise `1 − GC/Manual`. This conflicts with the positive-gain axes and the primary's explicit ratio examples. Preserve this **static sign discrepancy**; do not silently repair the formula, reinterpret all plotted points as exact recalculations, or claim the uninspected implementation is wrong. Absolute plots and author-stated examples support the scoped comparisons above. A ratio described as GC using150% more memory means2.5 times the manual amount, not a150% reduction from the GC baseline.

Ten TPC-H iterations are workload repetitions, not evidence of ten independent experimental runs. Guard/API preparation and runtime changes belong to the intervention.

## Consequence for Nu and next survey action

For B02/B04/B06, Snowflake adds explicit **lifetime ownership** to the comparison with [HistOOry](S247-histoory-object-history.md)'s selected field histories and [Tardis](S246-tardis-managed-history.md)'s checkpoint/replay. It answers when selected storage may be safely reclaimed; it does not retain an old logical state or decide which behavior should survive an edit. Static lifetime checks, correct historical values and intended temporal behavior remain separate obligations.

The favorable cache/memory results are useful evidence for a .NET alternative, while Infer.NET and Havlak reject a universal runtime or pause advantage. The [DATAS guidance](coreclr-datas-guidance-2026-10-04.md) adds a later GC-policy alternative at a different version and workload. None measures the current Nu revision's effective runtime/GC mode, retained world roots, frame tails, porting effort or net maintenance benefit. Those are explicit empirical residuals, not unread Snowflake-method gaps.

The next consequential survey action is **game-change and adoption evidence**: follow the game-practice corpus and primary engine-evolution reports to establish actual change families, integration work and developer outcomes. Reuse the now-reconstructed runtime mechanisms rather than automatically following every memory-management neighbor.

## Mechanism and obligations

**The implemented contribution is an external event monitor with application-owned state repair.** Lakitu extends the Java Infinite Mario Bros game; S278 calls the broader architecture Zenet, while S277 names the monitor Mayet. These accounts share the same demonstration lineage. They do not report replacing running source definitions, migrating successor schemas or comparing Nu-like live-code architectures.

| Boundary | Primary reconstruction |
| --- | --- |
| Observation and specification | Developers manually instrument meaningful events and write rules characterizing unacceptable states/sequences (S278 §§4.1–4.4, pp2–3; S277 pp55–57). Immutable event payloads contain selected values such as location, acceleration and score changes. High-level event contracts can survive implementation refactoring **provided that the contract and its meaning are preserved**. Manual event selection, payload design and correct emission remain obligations. |
| Rule evaluation | ActiveMQ/JMS routes events to Drools; received events enter working memory and trigger rule evaluation. The demonstrated monitor/broker run on the client machine; separate machines/languages are architectural possibilities, not evaluated comparative deployments (S278 p3). Drools/CEP supplies temporal matching. S277 p56 notes that a broker is optional for one instance and that the demonstration shares queues for simplicity. |
| Concrete temporal property | A jump with no landing timestamped within two seconds triggers downward movement after the rule's two-second delay (S278 fig3; S277 fig2b). This combines an event relation, a clock/deadline and retained monitor facts. S277 explicitly distinguishes bounded safety obligations from unbounded liveness (p55). It does not provide arbitrary-history preservation across edits/restarts or a proof for every possible temporal property. |
| Instrumentation completeness | In S277 p57 the authors first insert faults, then determine the observations needed to detect them. For falling below the screen, where no pit object/callback exists, they add a once-per-second position event. Event-rich source code does not itself guarantee detection; the required observation still has to be chosen and emitted. |
| Repair representation | S278 §4.5 lists four message types: `MarioMovement`, `DisableKeys`, `RemoveSprite`, `WriteBlocks`. The host interprets parameters and mutates its own state. Rules never directly write the game state. The authors identify repair-abstraction design as difficult: specificity grows the message vocabulary; generality loses expressiveness (p4). |
| Scheduling and stale state | The game polls for repairs every frame; S277 p58 locates application after logical-state updates. Asynchronous messages may describe an earlier state and need not correspond to the current loop iteration. The host may delay a repair, ignore it when irrelevant or schedule it outside the player's view. Synchronous waiting is a discussed option, not a measured alternative with a supplied cost comparison. |
| Preserved behavior | The running session continues and selected bad states are changed. Examples include reducing excessive jumps, ending hovering and inserting blocks into otherwise impassable generated gaps. No equivalence law says that all other game behavior, progress, pending work, effects or player intentions remain intact. S278's demonstration restart resets the game to level1 and clears monitor memory (p5). |

The rules and repairs are human-authored. S277 fig2's caption describes rules as generated, but the actual method explicitly attributes their construction to experienced programmers; the caption is not evidence of automated rule synthesis. The poster's possible future event-sequence inference likewise is not an implemented learning result.

## What the evidence supports

**Preserve the positive demonstration:** the authors show how on/off controls for seeded faults and the rule engine change the same game, provide rule/log examples, and show normal versus excessive jump screenshots. S278 fig8 also describes repairing an impossible generated gap by adding blocks. The separation between observed events, temporal constraints and host repair operations is concrete prior art for runtime recovery and useful design documentation.

This is one authored demonstration lineage across two publications and two presentation artifacts. The seeded faults, observations and repair rules are developed with knowledge of each other. There is no reported independent holdout fault set, developer experiment, player-acceptability study, net maintenance-cost measurement or production deployment. The demonstration procedure anticipates two-to-five-minute visitor sessions; it does not report sampled participants or measured completion times. Reconstructing it does not enact it.

**Cost and outcome claims have different scopes.** S278 describes one-or-two-frame lag and S277 describes recovery within a few frames; neither provides a latency distribution, frame-time table, reliability rate or a workload comparison. The two seconds in the hovering rule is the chosen detection deadline, not a measured repair latency. S278's cited ActiveMQ throughput exceeding30,000 messages/s is an external broker result, not measured end-to-end Mayet performance. Assertions that rules are orders of magnitude smaller, easier for nonprogrammers to validate, or liberate design are experience/expectation statements here, not comparative developer-benefit estimates.

**The limits are consequential, rather than reasons to discard the mechanism.** S277 identifies graphics-pipeline failures that the logical-state monitor cannot necessarily detect or repair (p58); the taxonomy sidebar marks graphical representation and implementation response outside its current coverage (p56). This is a capability classification, not a measured9/11 success rate. Repair cascades/loops and sending a hovering character into a spike pit are acknowledged possible failures, not reported observations with incidence estimates. The proposed mitigations—small changes and narrow rule matches—are not a termination or preservation proof. The authors explicitly say that scaling to a full game has not been attempted (p58).

The poster's commercial-scale assertion therefore cannot count as deployment evidence. Its time-rule heading says three seconds while the rule and explanation use two; its height example tests `jumpTime > 5`, whereas S277 uses `height > 5`. The poster omits the `duration(2s)` present in the paper and slides. These are recorded source/presentation differences, not silently reconciled into executable semantics. No code was compiled or tested to choose an interpretation.

## Consequence for Nu and next action

For B03/B04/B05/B08/B09/B12, separate **detecting a violation**, **selecting a repair**, **applying it to the current state**, and **preserving other obligations**. Mayet supplies a real recovery alternative with a developer-authored observation/repair contract. It narrows generic novelty in event-based temporal checking or continued execution after state repair; it does not establish a Nu implementation advantage or measured maintenance benefit. Declarative constraints can be useful while event selection, stale messages, rule interactions and host integration still consume engineering work.

The strongest next primary gap is the later *Automated Bug Finding in Video Games* lineage: ICST2014 DOI10.1109/ICST.2014.27 and the2017 Computers in Entertainment article DOI10.1145/2700529, with the2013 platform-game temporal-monitoring predecessor DOI10.1007/978-3-642-40787-1_23. Reconstruct actual games, fault populations, rule/monitor semantics, temporal coverage and measured costs after native registration/reuse. These may change the oracle and performance evidence beyond Mayet's authored demonstration. Keep the known architecture/access, practice, generation and type-evolution frontiers independent; no construction or additional worker is authorized.

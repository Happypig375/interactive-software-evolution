## Representation and correspondence

The [script model](https://github.com/edu-rinaldi/NodeGit/blob/764c4aaabf98548f8f9f824fce8fa3e74e69943c/lib/nodediff/script.h#L24) is a map of graphs, each a map of nodes. A node contains named values, node references, graph references, texture data and input connections. Connections are stored on the destination node and identify a source node/socket. The library explicitly assumes that nodes of the same type have the same property set. Client code supplies `get_node_type`; the Blender adapter uses the node kind and, for node groups, the group name. C++ reference wrappers distinguish graph and node IDs, while the actual property representation uses string keys and runtime value tags. This is not compiler checking of every future domain case.

The [Blender importer](https://github.com/edu-rinaldi/NodeGit/blob/764c4aaabf98548f8f9f824fce8fa3e74e69943c/examples/nd_blender/parser.cpp#L116) assigns fresh UUIDs to nodes on each import and to subgraphs, preserving the special main-graph name. It gathers subgraphs by their names and reconstructs parent, group and input references. Correspondence therefore must be inferred across imported versions; shared stable node IDs are not required. Node names are omitted from ordinary attributes, but group names affect the type classification. Renaming an ordinary node and renaming a group need not have the same matching consequence.

The complete [matching implementation](https://github.com/edu-rinaldi/NodeGit/blob/764c4aaabf98548f8f9f824fce8fa3e74e69943c/lib/nodediff/matching.cpp#L36) establishes these rules:

| Step | Pinned implementation | Consequence |
| --- | --- | --- |
| Match graphs | Sum absolute differences in node-type counts, normalized by the ancestor's node count; greedily accept costs strictly below 0.65. | Similar composition guides correspondence; names, behavior and user intention do not determine the graph score. |
| Match nodes within matched graphs | Different node types receive maximal cost. Otherwise count changed values, references, textures and input connections, divided by the ancestor's property count; accept costs strictly below 0.35. | Types and represented relationships narrow the search. Fixed property sets and nonempty normalization denominators are premises of the inspected cost path. |
| Update correspondence | Repeatedly scan unmatched pairs, select a cheapest admissible pair, remove it and recompute with the enlarged match map. Invalid references are initially paired. | Already matched references change later costs. This is greedy correspondence, with unordered traversal/tie choices, not a global optimum or recovered chronological edit log. |
| Compare values | Runtime tags and contained values/arrays are compared exactly; texture references are represented as value maps. | A selected graph/property edit is the unit. Texture-content matching and semantic equivalence are not supplied by these comparisons. |

The useful capability is concrete: a structural comparison can associate nodes whose import IDs differ and express a small property/reference delta, instead of treating every renamed identifier as an unrelated textual change. The source establishes how that capability is implemented; it does not measure its reliability on the paper's test population.

## Differences, conflicts and integration

The [diff implementation](https://github.com/edu-rinaldi/NodeGit/blob/764c4aaabf98548f8f9f824fce8fa3e74e69943c/lib/nodediff/diff.cpp#L235) emits whole-node/graph additions and deletions, and partial property maps for edits. References to matched objects are translated back into ancestor IDs, including references from newly added objects. Unmatched references keep version IDs. Same-type property comparison uses keyed lookup in the ancestor, consistent with the fixed-property-set premise; it is not a general schema-migration algorithm.

The complete [merge core](https://github.com/edu-rinaldi/NodeGit/blob/764c4aaabf98548f8f9f824fce8fa3e74e69943c/lib/nodediff/merge.cpp#L8) checks overlapping changes to the same node or graph: delete/edit clashes and different new values for the same edited property or connection. Different properties can combine, and identical edits are not conflicting. If conflicts are found, callers receive conflict records and the result is documented as unsuitable for use. Otherwise, the core copies the ancestor and applies the two diffs sequentially. The command-line wrapper first removes equal added-node payloads from the second diff. It supplies no interactive conflict-resolution policy equivalent to LevelMerge's preferred-branch handling.

**Source-level boundary, not an observed failure:** these checks do not inspect all cross-object consequences or run a behavior oracle. For example, deleting node A in one branch and adding a new node B that references A in the other branch concerns different changed IDs; the inspected conflict loop has no corresponding dependency-closure check. Sequential application can therefore leave a dangling reference in that constructed case. The exporter later looks up referenced nodes by ID. This follows from the inspected control flow; no test was built/run and no frequency or published-result contradiction is inferred. A successful local overlap check cannot be promoted to a guarantee of valid references, acyclic computation or intended merged behavior.

The [Blender command path](https://github.com/edu-rinaldi/NodeGit/blob/764c4aaabf98548f8f9f824fce8fa3e74e69943c/examples/nd_blender/nd_blender.cpp#L137) parses NodeKit JSON, computes diffs, writes a merged graph or conflict list, and exports JSON using a separate type/socket reconstruction description. It drops position/size edits from the final diff **after matching**, so layout can influence matching without surviving as a reported edit. The importer has a specific 16-slot encoding for multiple geometry-join inputs. These are concrete adaptation obligations, not a universal editor adapter.

Colored diagnostic output is also a separate artifact: the visualization helper reintroduces deleted nodes and clears their incoming connections to display them. The displayed history need not itself be the intended executable result. The inspected interfaces contain no migration of interpreter stacks, pending events/timers or external effects, and no running-game continuation contract. This keeps graph-document integration distinct from Nu's live-state/history claims.

## Nu consequence and continuation

Nu must be compared against tools that infer identity and combine represented edits, as well as approaches that preserve object IDs. The comparison needs an explicit representation/identity assumption, supported edit class, conflict policy, integration burden and behavior/effect contract. NodeGit's source closes the selected algorithm-understanding gap and adds a concrete domain adapter; its comparative evaluation remains an access gap. Neither this capability nor its limits establish Nu's net advantage.

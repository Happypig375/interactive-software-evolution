## Two distinct GUI-agent roles

The paper studies two roles whose information must remain separate.

1. **Development playtester.** Inside Play2Code, a rubric-blind GUI agent sees 1280×720 screenshots, a `GAME_GUIDE.md` written by the Game Agent, a fixed playtesting prompt, and selected GUI-side skill/world memory. It can screenshot, click, drag, press/type keys, scroll, wait and save memory. It has no reported source, DOM, console or internal-state access. It produces a chronological interaction log, outcome/confidence, per-dimension assessment, severity-tagged findings and a fix direction. A downstream parser reduces that report to a play summary and actionable fix list for the Game Agent (Appendix D.2, pp. 16–18).
2. **Final benchmark judge.** After a method stops, a separate GPT-5.5 GUI judge receives the generation prompt, generated artifact and full human-authored rubric, plays the build, and returns one binary verdict per criterion. It does not join the refinement loop, share Play2Code memory or feed scores back to the Game Agent (main §§3–5; Appendix D.3, p. 18).

This is a useful reported separation between current development feedback and final scoring. It does not independently verify information isolation: the complete prompts, memory state, parser, evaluator scaffold and run logs are not supplied in the inspected release. The development agent also receives a guide generated by the coding agent itself, so delivered documentation is part of the treatment rather than an external ground truth.

## Playing-feasibility study

Before using GUI agents as playtesters, the authors test three backbones on 20 intentionally simple browser games: ten frontier-model implementations lightly debugged by a human and ten static public games. Five genres yield **118 expert-defined levels** (reported as approximately 120 in the main text); action and shooter games are excluded because inference latency confounds real-time play. Each backbone–level pair receives 20 independent episodes of at most five minutes. Agents get the rendered screen and game guide, without rubrics or accumulated memory. Three human references use the same browser, viewport, guide and timeout, may make up to 20 attempts per level, and work in fatigue-bounded sessions (Appendix A, pp. 12–13).

Reported pass@20 is **.82 GPT-5.4, .79 Sonnet 4.6, .72 Kimi K2.5 and .92 human** (Table 1). Table 4's pass@10 genre means are .75/.76/.68/.92, with the widest gap on platformers. This establishes that these configured agents can complete many simple levels under repeated attempts. Pass@k means at least one successful episode, not single-attempt reliability. The games are deliberately simple, human-debugged or selected, and omit the latency-sensitive genres in the larger arena. The qualitative claim that observations are grounded, retries are informative and latency/low contrast dominate failures is an author analysis without a released coding or reliability procedure.

## PlaytestArena and the strengthened judge validation

PlaytestArena contains **200 self-contained HTML/CSS/JS generation tasks** in eight genres. Five non-author experts turn an initial 247 candidates into prompts and rubrics; a second expert and lead-author pass check concreteness, visual observability and prompt faithfulness. The final corpus has **1,548 criteria**, mean 7.7 and range **5–17**, covering mechanics, controls, progression, interface and visual feedback (main §3, p. 4; Appendix B, pp. 13–15). A score is the fraction of criteria the GUI judge marks passed. It is not a whole-game correctness, enjoyment, maintenance or lifecycle measure.

V2 replaces v1's 32-build validation subset with reported validation over **all 200 games**. Three non-author computer-science annotators with self-reported game experience receive each prompt and full rubric, play under the judge's ten-minute session budget, and issue forced PASS/FAIL labels while blind to generation method, GUI verdicts and GUI traces. Reported GPT-5.5–human agreement is **87.9%, κ=.66**, with game-level **Spearman ρ=.89 and Pearson r=.89**. Human–human values are **91.4%, κ=.68, ρ=.92 and r=.93** (Tables 2 and 5). This is materially stronger coverage than v1, while forced binary labeling still collapses failure to observe with observed failure and aggregate agreement does not exclude method-specific bias.

V2 adds two checks:

- Rejudging the same GPT-5.4-generated Direct LLM, OpenGame and Play2Code artifacts with Claude Opus 4.8 and Gemini 3.5 Flash preserves the method ordering. Scores vary—GPT-5.5 **31.6/55.7/72.3**, Opus **33.9/54.2/70.8**, Gemini **35.1/58.6/75.4**—and game-score correlations range **Pearson .86–.92 / Spearman .89–.94** (Tables 6–7). This tests judge choice for one backbone's generated artifacts, not every model, rubric or failure mode.
- An unspecified manual audit labels **46/50 trajectories (92%)** “successful playthroughs” when the agent identifies the objective, interacts meaningfully and reaches valid states (Appendix C.3, pp. 15–16). The paper does not report random selection, auditor identity, independent replication or coding reliability. The audit therefore bounds an observed sample; it cannot assign every low benchmark score to a broken artifact.

## Play2Code method, feedback timing and empirical comparisons

The Game Agent turns a prompt into a game design, assets, code and guide, runs build/headless checks, and stores memory. From round two onward it normally skips design/assets, reads the preceding GUI summary/fix list, chooses which advice to accept and revises the artifact. The GUI agent then plays the new build and reports. Episode memory retains within-task attempts and fixes; separate role-specific skill memory and shared world memory carry information across tasks. Task order, initialization, cross-task schedule and a held-out transfer protocol are still not reported, so games are not independent memory-free repetitions.

The main scores are unchanged from v1: **29.7% Direct LLM, 52.2% OpenGame and 66.8% Play2Code** averaged over three backbone columns, with every corresponding genre/backbone cell favoring Play2Code (Table 3). The closer GPT-5.4 ablations are also unchanged: **64.1 no accumulated memory, 69.3 episode only, 71.8 episode+skill, 72.3 full**, and **58.7 self-verification without a GUI agent** (Tables 9–10). These are favorable benchmark results. The nested single-sequence ablations have no repeated-run intervals and do not identify statistically additive or task-independent memory effects.

The pipeline contrast remains unequal. Direct LLM receives one generation; OpenGame gets up to five code/build inspection rounds and stops at a stable non-crashing build; Play2Code gets up to five code/play rounds plus cross-task memory and stops early when its development GUI agent reports `completed` or `reached-ending` with high confidence. The paper reports mean effective Play2Code rounds **3.24**, median **3.05**, SD **.72**, and **93.5%** stopping before round five (Appendix E, pp. 17–18). A per-task round count is an integer, so the fractional median leaves the aggregation unit unresolved—potentially a summary across backbones or repetitions—despite the text describing 200 tasks. V2 newly reports average inference cost on a random 10% GPT-5.4 subset: **$5 Direct LLM, $12 OpenGame, $17 Play2Code** (Table 8). The sample identities, repetitions, calls/tokens, pricing basis, browser/tool costs, wall time and human work are not reported. This partial cost estimate makes the resource difference visible but does not equalize the methods or establish net efficiency.

Final rubric scores are reported after each play/code round in Figure 6a, yet v2 still does not state how games that stopped early contribute to later-round averages or to the five-round gain used for grouping. A shrinking survivor population, carried-forward terminal scores and counterfactual extra rounds imply different estimands. Group averages also do not show monotone retained behavior for each game or criterion.

## Gain groups and the unresolved human comparison

V1 called outcome-defined groups High/Moderate/Low “complexity” terciles even though its printed thresholds and plotted trajectories were inconsistent with those labels. V2 improves the interpretation: the groups are now **limited gain** (Δ≤10), **moderate gain** (10<Δ≤15) and **large gain** (Δ>15), based on observed five-round rubric-score change averaged over the three backbones. They are fixed-threshold empirical groups, **not terciles**, not equal-sized, not an independent difficulty measure and not evidence that complexity causes improvement. The moderate group contains 50 games (main §5, Fig. 6a; Appendix G, p. 19).

The rendered curves do not fully follow the revised labels. Reading approximate endpoints from the axes, the panel labelled **Large gain** rises by roughly 10–13 points across its three backbone curves, which fits the printed moderate threshold rather than Δ>15. The **Moderate gain** panel rises by roughly 18–22 points, which fits the printed large threshold rather than 10<Δ≤15. The **Limited gain** panel's roughly 5–6-point changes agree with Δ≤10. These are visual estimates from the plot, not reconstructed row-level results; the underlying game assignments and scores are unreleased. V2 therefore corrects the causal terminology and false tercile claim, but appears to leave the first two quantitative panel labels interchanged. Post-outcome grouping and the early-stop population gap also remain.

The human-refinement comparison remains unresolved. Five computer-science graduate students each handle a disjoint share of the 50 moderate-gain tasks, one person per task and up to five rounds. Humans see the generation prompt and submit free-form reports; they receive no rubric and write no explicit human-side memory, while the Game Agent retains its Episode/Skill/World memories. The GUI condition instead receives a generated guide, emits a structured trace/report and can update GUI-side memory. Human labor and session cost are not reported.

Appendix H states that human-driven refinement scores higher in every round, especially later. At 300 DPI, the rendered Figure 6b instead places the gray Human curve slightly **above** green GPT-5.4 in rounds 1–2, then green GPT-5.4 **above** Human in rounds 3–5; the legend unambiguously assigns those labels. The text and plot therefore agree only in the first two rounds and conflict in the last three. V2 does not explain the crossing, so neither claimed overall direction is accepted as established. The differing inputs, report structures, trace requirements and memory treatment would also prevent interpreting the comparison as a clean human-versus-GUI capability effect even if the direction were corrected. Claims that GUI traces are intrinsically more traceable than human feedback reflect the logging protocol chosen for each condition, not a matched test of possible human logging.

## Consequences for R08 and R05

V2 supplies a useful pattern for R08: development feedback can be rubric-blind, behavior-grounded and actionable while final scoring is performed later by a disjoint role with separate resources. A Nu study should preserve that separation explicitly in the recorded information sequence. The candidate should receive only declared current source, tools, diagnostics and behavioral observations; final obligations and scores should never enter repair or stopping. A development-agent claim of `completed` may stop work, but it is not final correctness.

The paper also sharpens what must be recorded rather than copied wholesale:

- The generated game guide, screenshots, viewport/scaling, system prompt, memory slices, tool inventory and prior summaries are delivered information and potential treatments. Record their exact versions and sequence.
- Cross-task Skill/World memory changes the experimental unit. Disable it for independent assigned tasks or predeclare order, initialization, reuse and held-out transfer if cumulative experience is the question.
- Keep the full ordered interaction trace, inputs, observations, waits, phase/time basis and omitted ranges. Play2Code's reduction to a summary and fix list may be useful assistance, but it cannot substitute for R05's order/multiplicity evidence.
- Separate candidate generation/tool costs, development play/observation costs, final judge resources and human preparation. V2's $5/$12/$17 sample is evidence that GUI feedback adds cost, not a complete total-work measure.
- Preserve unknown or unobserved final obligations. Forced PASS/FAIL judging and a successful-playthrough audit do not eliminate GUI-agent observation failures.

For R05, the paper demonstrates screenshot-and-input feedback for browser games but does not establish a phase-correct temporal observer. Agents choose when to act, the feasibility study imposes no fixed tick, and precise timing is a reported failure mode. The GUI layer cannot observe Nu entity identity, internal event multiplicity, hidden state, native contacts, audio or retained world history unless those are deliberately exposed. A chronological visual trace can complement compiler/tests and structured event observations; it cannot replace them. The paper's claim that play reveals failures missed by code-level checks is scoped evidence for a combined feedback design, not evidence that static, formal or event-level oracles are generally inadequate.

The work evaluates fresh browser-game generation, not maintenance of retained requirements, exact event semantics, live-state preservation or Nu/F#/Godot development. Its favorable rubric gains therefore justify GUI feedback as a candidate method component while leaving the proposed Nu workflow, transport, security, phase access, independent scoring and practical benefit unresolved.

# Nu collaboration: scene integration and cross-role handoff

**Disposition:** R11's first artifact, ownership and outcome contract is specified; team comparison remains deferred. This is passive preparation under [PLAN](../PLAN.md), using Nu commit `064f7ae92a8506689cd91aff5e6804a375d6ef3d` and completed literature reconstructions. No scene variant, merge, editor session, adapter, candidate or participant study was constructed or run. The cases below are **authored from source**, not mined collaboration incidents or observed failures.

## Decision and credible comparison

Ask whether a workflow helps collaborators deliver a correct integrated change with less total work, including negotiation, translation between representations, integration and verification. A faster textual merge or one role's shorter editing time is insufficient. The first boundary is **quiescent source/scene authoring followed by fresh loading**. Active gameplay, pending events and irreversible effects belong to separate R03/R10 contracts.

Nu's serialized groups, source handles and Gaia operations provide an actual handoff surface. This inspection establishes no dedicated collaborative merge facility or Nu-specific merge advantage. Ordinary Git comparison, communication, manual repair and editor inspection are a credible starting workflow; allow those facilities in both packages of a later comparison. A semantic merge tool would be a separately justified treatment with its adaptation cost, not an assumed Nu feature. Do not force collaborators to work silently or repair every change manually to make a preferred tool win.

Keep two possible questions distinct: a package comparison with a common ordinary integration policy, and a within-package comparison of an **existing, verified** coordination/history facility. The latter currently lacks a verified Nu treatment. If a useful treatment and practical decision cannot be identified, retain this contract as R02/R12/R14 task and cost support rather than claim a standalone R11 contribution.

## Authored cases and accepted integrated outcomes

Freeze a common ancestor, both branch requirements and a feasible combined requirement **before assignment**. Each branch must be valid for its own request, not deliberately broken to make integration hard. Preserve actual patches, source/asset identities, build context and any failed attempt. These are coverage contrasts, not prevalence estimates or a fixed task quota.

| Case | Separately intended changes | Accepted integration and discriminating observation |
| --- | --- | --- |
| C1: different properties | One branch changes the Play button's visible label; the other changes its position within a declared usable layout. Neither changes its name or action. | The single intended button retains both edits and still enters Gameplay. Check the declared viewport, clickable region and retained Credits/Exit behavior; parsing and a conflict-free diff do not establish these. |
| C2: rename plus presentation | One branch renames the Play entity to Start and updates its F# handle while retaining its action. The other changes the original button's label/layout. | One intended Start button has the new presentation and correct click routing; no unintended old Play duplicate or lost edit. The combined requirement explicitly identifies the same conceptual button. Tools may use manual correspondence or safe reorganization; preserving a runtime Id or a particular diff shape is not mandatory. |
| C3: incompatible same-property choices | Branches give the same button different final labels or positions, each acceptable alone. | A declared resolution policy or recorded negotiation selects the accepted result. A single-valued property cannot retain both incompatible values. Record which request was revised and why; do not score every discarded value as a defect or automatic branch preference as preservation of all intent. Negotiation time belongs to the workflow. |
| C4: deletion with an outside dependency | One branch removes a button and its known routing; the other adds a separately valid use/reference to that button. | Specify beforehand whether the combined product retains the button or removes it and redirects/removes the new dependent behavior. Verify that resolution across scene and source. Structural validity, compilation and author-intended behavior remain separate checks. This is conditional follow-on coverage, not an invented existing Nu incident. |

C2 is the first consequential source-supported contrast because it connects serialized identity to an actual external event handle. C1 is a simpler reference case; C3 prevents an impossible preservation criterion. C4 is warranted only if the selected practical work includes deletion/dependency changes. Shared prefab revision, nested reparenting and live-state integration require their own obligations and are not silently included.

For the first contract, stop authoring and identify outstanding in-memory changes before integrating. Record whether the receiver starts a fresh session, explicitly reloads, or resumes a stale editor; do not pool these policies. Fresh-load success says nothing about a later save from stale memory. If stale-editor behavior becomes the practical question, predeclare the interleaving, each author's durable and unsaved edits, warnings and accepted reconciliation; source inspection alone supplies no result. Verify the exact source/build/deployed artifacts used for every eventual behavior check.

## Roles, handoff and total work

The provisional roles are **presentation author**, **behavior author** and **integrator/verifier**. They describe responsibilities, not recruited populations, independent participants or immutable job titles. One person can occupy several roles. Record each person's actual access, expertise, edits and assistance; a restricted presentation-only condition and unrestricted collaborative repair answer different questions. No real designer has yet validated the proposed case or its importance.

The sender's handoff identifies the ancestor and delivered revision, changed requirements/artifacts, intended correspondence such as Play→Start, unresolved choices and available verification evidence. Freeze which of this information is supplied as a task input and which must be produced during work; count production costs. It must not reveal a hidden successor solution or final scoring tests. The receiver must be able to locate the correct revision, understand the required changes and independently verify the integrated result through supported access. A programmer interpreting or repairing a designer's artifact is assistance to record, not free tool functionality.

Measure elapsed delivery time and the **sum of active work across people** separately. Count simultaneous joint work for every active contributor, alongside waiting/coordination delays, preparation and training, authoring, conflict inspection, negotiation, integration, reload/deployment, verification and rework. Report tool/compute use and any adapter/support preparation separately and in the declared total-cost boundary. A faster pair is not automatically cheaper than one person. Do not condition effort comparisons only on correct completions or omit abandoned, unrecoverable or rescued attempts.

Preserve outcomes at several boundaries: textual conflict status; descriptor/load success; identity/reference consistency; new and retained behavior; each role's ability to continue; and unresolved/missing evidence. A warning or conflict counter is diagnostic exposure. Clearing it does not prove the final obligation. Keep team/task assignment, repeated work, order and learning explicit; two collaborators and their repeated edits are not independent teams. Participant numbers and statistical methods follow a separately justified human design, not the number of authored cases.

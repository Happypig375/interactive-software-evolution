# Nu/Jolt recovery dependency and fix lineage

**Passive source/artifact audit, 2026-10-11.** This follows the R17 dependency identified in the [Nu history audit](nu-source-contracts-and-scenarios-2026-10-11.md). It also refines R03/R06's native-reconstruction boundary. Nu remains pinned at `064f7ae92a8506689cd91aff5e6804a375d6ef3d`. No package restore, native library load, engine run, compiler/model probe, baseline or new adapter is performed. [PLAN](../PLAN.md) retains the holds and zero allocation.

The package-to-vendored-binary identity is now verified, and the upstream zero-time contact-callback fix is located. **The exact Jolt source revision used to build those binaries remains unverified.** More importantly, Nu's inspected integration path does not call the native update at zero elapsed time. An upstream fix therefore does not by itself remove Nu's maintenance policy or establish its current correctness/cost.

## Nu's current policy still matters

[Nu #957](https://github.com/bryanedds/Nu/issues/957), [#958](https://github.com/bryanedds/Nu/issues/958) and [Jolt #1520](https://github.com/jrouwe/JoltPhysics/issues/1520) remain the already-read public practice lineage. They describe undo/rebuild tree exhaustion, periodic optimization as a workaround, possible pauses and discussion of zero-time maintenance. Their present text and maintainer explanations are not reproduced current failures. #958 itself qualifies whether pauses would be noticeable.

The pinned [creation route](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/Physics/JoltPhysicsEngine.fs#L807) increments `BodyUnoptimizedCreationCount` and calls `OptimizeBroadPhase` at a configured threshold, then resets the counter. Its [default](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/Core/Constants.fs#L383) is `128 * 3`, with a mutable uniform setting. This is the counter in that route, not automatically the live-body count or an exact count of every native allocation.

The [integration path](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/Physics/JoltPhysicsEngine.fs#L1535) invokes native `Update` only when `gameDelta.SecondsF > 0`; otherwise it returns no integration result. It also handles characters, constraints and output messages when advancing. Thus calling the existing Nu integration method with a zero delta would not exercise Jolt's zero-time maintenance branch. The [clear path](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/Physics/JoltPhysicsEngine.fs#L1638) removes bodies/constraints and clears contact/message state but does not reset that creation counter or replace the whole physics context. This source distinction matters for repeated restoration and cumulative creation work.

The wrapper's [PhysicsSystem methods](https://github.com/amerkoleci/JoltPhysicsSharp/blob/da6da06e703b0d8cc4908247ba2d49e03b7c29f8/src/JoltPhysicsSharp/PhysicsSystem.cs#L213) and [native imports](https://github.com/amerkoleci/JoltPhysicsSharp/blob/da6da06e703b0d8cc4908247ba2d49e03b7c29f8/src/JoltPhysicsSharp/JoltApi.cs#L1628) expose both update and broad-phase optimization. Its [BodyInterface](https://github.com/amerkoleci/JoltPhysicsSharp/blob/da6da06e703b0d8cc4908247ba2d49e03b7c29f8/src/JoltPhysicsSharp/BodyInterface.cs#L28) exposes single-body create/add/remove operations. Whole-file keyword/declaration inspection of BodyInterface and JoltApi finds no `AddBodies`, `AddBodiesPrepare` or `AddBodiesFinalize`. This is a bounded statement about those pinned binding files, not all possible native extensions or newer packages. Upstream advice to batch is not a ready managed operation established by this audit.

## Consequence for R17 and R03/R06

R17 now has an authentic cross-layer case: a functional history workflow rebuilds an imperative subsystem; upstream maintenance/callback semantics, binding coverage, vendored binary provenance and Nu's event policy determine which remedies are actually available. It is more substantive than simply updating a package number, but its prevalence, practical cost and generalizable research contribution remain unmeasured. Keep its priority conditional; source complexity alone does not show that integration dominates the maintainer's work.

| Prospective alternative | Current evidence | Requirement before any comparison |
| --- | --- | --- |
| Existing periodic optimization | Present in Nu and exposed by the pinned wrapper. | Count cumulative creation/restoration and actual configured threshold; observe complete restore/resume work, contact/lifecycle behavior and frame-time tails. Preserve outcomes with no noticeable stall. |
| Explicit zero-time native maintenance | Supported by the named upstream release's inspected path and the wrapper's update API; bypassing Nu's positive-time guard requires a deliberate integration change. | Establish actual loaded binary semantics and a safe call phase; preserve paused state, callback/effect policy, characters/constraints and subsequent valid contacts. An upstream unit test alone is insufficient. |
| Batched body insertion | Recommended in the historical native discussion; no matching batch-add operation found in the selected managed declarations/imports. | Verify a supported binding route or separately authorize the required integration work. Do not treat a new adapter as free setup or silently construct it under the literature permission. |
| Differential reconstruction | Mentioned by the Nu maintainer as a possible alternative to full rebuilding. | Specify ownership, identity/contact/cache invalidation and the observation contract before implementation. It is a different, unbuilt policy, not an existing cheap control. |

These are preparation options, not four allocated arms. R06 should distinguish scene size from cumulative creation and restoration frequency, keep functional execution mode fixed, and include native maintenance plus first-resumed-frame behavior. R03 must state whether it promises represented values or native-contact continuation. A contact cache/callback difference after reconstruction is a required observation when that continuation is promised; it is not automatically evidence of an application-visible bug.

**Remaining boundary:** exact joltc/Jolt build provenance for the vendored binaries, actual resolved/loaded artifacts and behavior under the selected application are unverified. Public build/release attestations or an identifiable source/build record could close the first gap passively; restoration and behavior probes remain held. Do not upgrade an inference to a verified fix or change dependencies in this research checkout. Continue the independent R03 application/state-subset work while retaining this specific uncertainty.

# A selected application contract for Nu history

**Decision, 2026-10-11:** use the existing MMCC Breakout in **functional Gaia, under unchanged code**, as the first bounded R03 technical case. Its explicit gameplay model makes a useful restoration obligation inspectable. This is a source-supported eligibility choice, not a successful launch, verified replay or representative debugging benchmark. The [operation audit](nu-source-contracts-and-scenarios-2026-10-11.md#r03-what-gaia-restores) and [study packet](nu-research-study-designs-2026-10-08.md#r03--history-assisted-debugging-and-recovery) retain the larger question. All construction and execution holds in [PLAN](../PLAN.md) remain; new allocation is zero.

The first comparison should establish correct recovery of a noninitial declared state, then account for the work needed to reach it. A later debugging extension would need real faults, permitted agent access and an independent repair endpoint. A toy model restoring successfully alone would not establish a consequential research contribution or human benefit.

## Source and execution eligibility

All Nu references use `064f7ae92a8506689cd91aff5e6804a375d6ef3d`. Nineteen pinned files were acquired and hashed locally; selected bodies were inspected, with eighteen new/material source decisions. Earlier generic `World.switch` evidence is reused without another screening credit. The [search ledger](literature/nu-background-searches-2026-09-30.md) records actual ranges. No new publication, Zotero mutation, compiler/runtime probe, baseline or observer was added.

The standalone [Program.fs](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Projects/Breakout%20Mmcc/Program.fs#L23) overrides SDL configuration only. [`WorldConfig.defaultConfig`](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/World/WorldPrelude.fs#L374) sets `Imperative=true`, `Accompanied=false` and `Advancing=true`. That entry point is therefore not an automatic control for functional history. [Gaia's configuration](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu.Gaia/Gaia.fs#L4613) takes its execution mode from `ProjectImperativeExecution`, starts accompanied and halted, and chooses a project edit mode. The actual persisted setting and supported launch remain unobserved. Both recovery arms must use the same verified functional mode.

The [Gameplay edit mode](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Projects/Breakout%20Mmcc/BreakoutPlugin.fs#L16) initializes the screen model and sets the game model. The [top-level dispatcher](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Projects/Breakout%20Mmcc/Breakout.fs#L42) requests the Gameplay screen. [Selecting that screen sends `StartPlaying`](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Projects/Breakout%20Mmcc/Gameplay.fs#L203), which initializes the model again. A later reconstruction must settle selection/transition handling before asserting the target model; writing a model and then triggering selection could replace it. The exact launch/transition sequence has not been exercised.

## What this application's model can represent

The [Gameplay record](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Projects/Breakout%20Mmcc/Gameplay.fs#L54) contains time, a Playing/Quit case, paddle and ball records, a map from string brick names to brick records, score and lives. The inspected application records have no mutable fields or array/object-valued payloads; their numeric vectors and [Color struct](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu.Math/Color.cs#L19) carry values. This is a reason to choose this model, not proof that the entire reachable world is immutable.

Ordinary [screen model setting](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/World/WorldModuleScreen.fs#L158) creates a replacement screen-state record, updates its map, synchronizes content and publishes a model-change event. However, [ScreenState](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/World/WorldTypes.fs#L1078) includes mutable model/extension fields, and [generic model conversion/fallback](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/World/WorldModuleScreen.fs#L140) can write the model in place when its type differs. The proposed case excludes reload, schema/type replacement and arbitrary user mutation. That boundary is essential to the source argument.

The [content projection](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Projects/Breakout%20Mmcc/Gameplay.fs#L258) uses the model for paddle/ball positions, brick names and positions/colors, score text and life icons. The application performs its own ball motion/collision calculation. Its [StaticSprite](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/World/WorldDispatchers.fs#L53) and [StaticModel](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/World/WorldDispatchers.fs#L514) dispatchers are inspected, and the project's overlay is empty. These facts motivate separating this application-model case from an ImSim/native-physics continuation case; they do not prove that the whole world has no native resources or reconstruction cost.

The small [scene asset](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Projects/Breakout%20Mmcc/Assets/Gameplay/Scene.nugroup#L1) names a Unit model with FSharp.Core assembly version 7.0.0.0, plus skybox/light entities. The engine package declaration examined previously is 10.1.300. This is an asset/version preflight item, not a demonstrated loader incompatibility: exact loader resolution and a supported launch were not inspected or run.

## Checkpoint and observation contract

Choose a reachable, settled Gameplay screen with noninitial model values, then a checkpoint captured while halted. A useful authored eligibility example is a state after a brick has been removed and the score changed, so fresh initialization would not accidentally satisfy restoration. Actual reachability, input sequence and checkpoint selection still require later authorized validation. This is one application, not a mined failure or several independent tasks.

[Advance/halt snapshots occur before toggling the flag](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu.Gaia/Gaia.fs#L1395). A Halt-labeled checkpoint can therefore contain an advancing world. The Step command instead snapshots a halted world before enabling advancement; [the later ImGui processing path](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu.Gaia/Gaia.fs#L4301) turns advancement off when `Stepping` is set. [Ordinary undo/redo](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu.Gaia/Gaia.fs#L617) do not impose an unconditional halt. Record the actual checkpoint kind and stored mode; the Step label alone is not an executed one-frame guarantee.

Define **B0** as completion of the chosen undo/switch and Gaia's selection/camera reconciliation, before another advancing gameplay update. Define **B1** as the declared subsequent application-event boundaries after controlled resumption. Those are proposed observation points, not currently verified hooks or agent tools. Failure to obtain B0 before more updates is an observation limitation, not automatic evidence of faulty retention.

| Boundary or component | Required observation | Limit or valid alternative |
| --- | --- | --- |
| Eligibility and B0 mode | Functional, accompanied execution; intended selected screen with settled transition; stored advancement flag agrees with the chosen checkpoint. | A different mode or newly initiated screen selection is not the same recovery case. Actual mode and transition access must be validated. |
| B0 application values | Saved GameplayTime, case, score/lives, paddle/ball components and brick map keys/values match the checkpoint fields, including stored floating-point values. | A fresh model that happens to look similar is insufficient. No requirement for the same CLR object addresses is imposed. |
| Logical identity and projection | Preserve the checkpoint's brick keys and intended screen/entity addresses; after the declared content boundary, rendered-state properties and HUD correspond to the recovered model. | Across a fresh-world comparator, newly allocated internal/native IDs may differ unless a separate requirement makes them observable. A screenshot alone does not establish model or lifecycle agreement. |
| B1 logical time and update order | Record the actual Update/TimeUpdate boundaries and justified horizon; compare state at matching logical points. | Matching wall-clock duration or editor frame count is not sufficient. Do not infer a one-step schedule solely from button naming. |
| B1 input and branch behavior | Declare the keyboard values and focus/capture policy available to both continuations; exercise required motion/collision behavior. | Uncontrolled input or a missing required trigger yields an unverified/inconclusive continuation, not a pass. Program failure to reach a required trigger remains a failure under its requirement. |
| B1 effects | If effect requests are included, specify their multiplicity and order within the resumed branch and observe the actual boundary. | Replaying a collision can legitimately request sound again. Sound already heard before undo is outside the rollback promise. |

The [clock selector](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/Core/GameTime.fs#L28) is the mutable `Constants.GameTime.DesiredFrameRate`, whose source default is `StaticFrameRate 60L`; it can be changed through [application configuration](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/World/WorldConfigure.fs#L19). `FramePacing=false` does not select static timing. [Ambient game-delta selection](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/World/WorldPrelude.fs#L557) depends on that clock selector and advancing state. The first proposed case freezes static timing, with its effective value verified later. Gameplay's separate TimeUpdate adds the game delta's updates; host stopwatch/date equality is excluded.

The [keyboard query](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/World/WorldInput.fs#L113) reads current keyboard/ImGui state and does not use its world argument. Retaining a world is therefore not evidence of a recorded input stream. [Ball initialization](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Projects/Breakout%20Mmcc/Gameplay.fs#L35), brick colors/names and ball respawn also use generated values. Saved realized values belong to B0; the operation audit establishes no RNG rewind for future draws. The first B1 case must declare a bounded prefix that does not require a new draw. A life-loss/respawn or reinitialization case needs its own randomness contract, not unexplained exact-trajectory scoring or removal of unfavorable attempts.

## Comparator, costs and falsifiers

Compare retention/restoration with **fresh functional initialization plus reconstruction of the same B0 contract**. Count the latter's checkpoint-data acquisition, selection/transition work, model restoration, identity/content reconciliation and required readiness work. The existing [GetGameplay/SetGameplay](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Projects/Breakout%20Mmcc/Gameplay.fs#L183) accessors and [screen model API](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/World/WorldScreen.fs#L29) are potential in-process routes, not a built reconstruction procedure. Setter synchronization/change publication differs from root switching; common observations must establish equivalence. If fresh reconstruction cannot meet the declared contract with supported operations, report that limitation instead of treating an incomplete cheap restart as a valid cost comparator.

For retention, count checkpoint creation, retained reachability, undo/redo bookkeeping, native/spatial reconstruction, the first resumed work and release. Even this model-focused case uses [`World.switch`](https://github.com/bryanedds/Nu/blob/064f7ae92a8506689cd91aff5e6804a375d6ef3d/Nu/Nu/World/WorldModule2.fs#L993), which rebuilds engine services. The [Nu/Jolt audit](nu-jolt-dependency-audit-2026-10-11.md) remains relevant to those costs without making exact native trajectories a B0 obligation. No bounded eviction or ready history-off switch was found in the earlier Gaia audit; do not claim a retention-policy experiment already exists. Same-mode accounting avoids attributing an imperative/functional execution difference to retention alone.

These authored falsifiers make the limits reviewable before execution:

- A later state has fewer bricks and a higher score, but undo recovers only the displayed ball position: B0 fails even if the image looks plausible.
- B0 values match but the next content boundary creates a wrong brick or HUD state: the stronger projection obligation fails; model restoration and content continuation stay separately reported.
- A Halt snapshot resumes advancement before a delayed observer reads it: the observation phase is invalid for the halted-checkpoint design; this alone is not a retention defect.
- A resumed life-loss branch chooses a different random ball direction: exact replay was not established for that branch. Preserve it as outside the first B1 contract until randomness is specified.
- Fresh reconstruction meets every declared obligation at lower total cost, or history restores correctly but retained memory/tails dominate: both are useful adverse results for the proposed workflow.

These are specification examples, not executed traces, injected faults, independently sampled tasks or final tests. No post-outcome exclusions or favorable replacement runs are authorized.

## Readiness and next decision

R03 now has a selected first application, mode, represented-value boundary, checkpoint policy, continuation limits and same-work comparator requirement. **B0 feasibility remains conditional on launch, phase/access and model/content correspondence; B1 additionally needs controlled input/timing and the selected horizon.** The agent extension remains deferred: in-process getters, Gaia's console and a GUI history list do not establish a permitted agent transport. No adapter or task-solving observer should be inferred from this design.

Continue independent source/task work on credible R02/R04 diversity and R01's common requirements. Revisit a literature method only when it changes the selected comparison or observation contract. Exact native build/replay work is consequential if a promoted case actually promises native continuation. The next step for this specific B0 contract is a separately reviewable feasibility/construction decision; more generic snapshot reading cannot certify a runtime, repair benefit or useful effect size.
